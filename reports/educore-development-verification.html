1. Fixture guard: root cause and safe correction

The previous cleanup classifier recognized the older promotion-history protection but rejected the newly introduced immutable security-event and security-operation-history triggers. Treating those tables as ordinary deletable fixture tables would violate their history protections.

  • The guard now recognizes exactly three immutable protections: promotion history, security events and school security operation history. It validates enabled state, trigger events, function/schema identity, canonical function body, argument count and security-definer state; altered, missing or unrecognized protections still fail closed.
  • History-bearing fixtures use logical retirement, not a trigger exception. Ownership is verified against the unique fixture school name/code and seven exact fixture identities. The transaction disables the owned school, users, memberships, device, students, parents and employee; revokes device credentials; marks active owned cards lost; and removes only owned, derived campus-presence rows.
  • Security events, operation history, audit records, attendance, communication records and their referenced identities remain. No security trigger was disabled or rewritten; no constraint or foreign key was dropped; no database reset was used.
  • Baseline row multisets and original columns are checked transactionally. Additional legitimate QA/audit rows are allowed, but every original row must survive unchanged. The older baseline intentionally excludes newly added archive/emergency fields from old-row comparisons.
  • This is an offline Development fixture/operator mechanism, not an application cleanup API. Normal application immutable-history protections remain active. Verified owned Development Clerk users are deleted after database retirement.
