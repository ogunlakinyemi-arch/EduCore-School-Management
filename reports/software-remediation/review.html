Mandatory gates before any database-change proposal

  1. Obtain explicit authorization for the intended environment and operation. Independently verify the application's actual database target; environment labels and database names are insufficient.
  2. Confirm the actual hosting provider and available backup/PITR mechanism, a backup preceding the change, retention, restore permissions and acceptable recovery point/time. No backup was inspected or restored during this work.
  3. Demonstrate recovery in an approved isolated environment. Replit-managed databases offer production recovery options, but this must not be assumed to apply to an externally configured database. Database restoration and code rollback are separate operations.
  4. Produce a fresh, reviewed incremental preview against the verified existing target. Confirm parent uniqueness precedes every dependent FK, no destructive/data rewrite statements are hidden, existing CHECK differences are represented, and retained records are accounted for.
  5. Execute the exact reviewed plan only in an already configured and approved disposable PostgreSQL instance first; compare raw versus reordered results, constraints, migration ledger and preservation evidence. None was available in this remediation.
  6. Request separate approval before any Production access or execution. Current status: not approved; not executed.
