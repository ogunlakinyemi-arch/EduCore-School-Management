D. Semantic Comparison

Device class

HISTORICAL: Composite only: platform_devices_class_school_fk; MATCH SIMPLE; NO ACTION delete/update; NOT VALID.

CURRENT: Nullable inline school_class_id → school_classes(id), plus separate class/school composite. Both default NO ACTION delete/update. Current-model disposable catalog validates both; deployed state not queried.

DIFFERENCE: school_id and school_class_id nullable. Any NULL skips composite matching. Standalone rejects a missing non-NULL class even with NULL school. Both allow an existing class with NULL school; neither itself requires paired unassignment. Composite enforces class belongs to assigned school when both fields are non-NULL. Standalone alone does not. Actual current dual design retains that protection for checked writes; NOT VALID historical FK still enforces new writes but does not certify old rows.

RISK: Legacy mismatched class/school pairs can block validation; orphan class IDs with NULL school can block a standalone addition. Dropping standalone allows orphan nullable-school class references; dropping composite allows cross-school class references. Do not silently clear/reassign existing devices to make an audit pass.

Allocation student

HISTORICAL: Direct composite student_subscription_allocations_student_school_fk; both columns NOT NULL; ON DELETE RESTRICT; ON UPDATE NO ACTION; validated creation.

CURRENT: Inline student_id → students(id) ON DELETE RESTRICT; ON UPDATE NO ACTION. No direct student/school composite. Retained payment_owner_term FK binds the ledger to the payment snapshot, not to students.school_id.

DIFFERENCE: student_id and school_id are NOT NULL in both designs, so neither can bypass its constraint through these NULL fields. Current standalone is weaker for tenancy, not for student existence. Historical composite directly prevents cross-school student references. Standalone does not. Payment → subscription → global student FK chain still permits an internally consistent but wrongly school-bound subscription/payment tuple. Synthetic owner-chain projection demonstrated that gap; application same-school JOIN excludes the synthetic mismatch.

RISK: Existing allocations with student/school mismatches would reject new validation. A future move of a referenced student to another tenant would be blocked by NO ACTION on the composite; synthetic examples demonstrated this. No such real rows or transfer workflows are asserted. Preserve append-only financial records; do not rewrite IDs or school ownership merely to satisfy a constraint.

Allocation attribution

HISTORICAL: Composite attribution_partner_fk(attribution_id,recipient_id) → (id,partner_profile_id); ON DELETE RESTRICT; ON UPDATE NO ACTION; MATCH SIMPLE; validated creation. Recipient CHECK requires attribution/recipient/rule for PARTNER, but permits NULL recipient and optional attribution for non-PARTNER.

CURRENT: Inline attribution_id → school_partner_attributions(id) ON DELETE RESTRICT, plus retained attribution/partner composite with default NO ACTION delete/update. CHECK unchanged. Current-model catalog validates both. Logical standalone name exceeds PostgreSQL limit; physical name preserved separately.

DIFFERENCE: attribution_id and recipient_id nullable; school_id NOT NULL. Composite skips matching when either member is NULL, but PARTNER CHECK prevents NULL attribution/recipient on PARTNER rows. Non-PARTNER NULL recipient is legitimate and intentionally paired with a non-NULL attribution by the writer when the school is attributed. Standalone protects existence and RESTRICT deletion of that metadata. Partner-pair composite checks correct recipient Partner, not school. Standalone checks existence, not school. Both accept attribution from another school with the same Partner, or a valid cross-school attribution on a non-PARTNER row. Current writer prevents this through WHERE a.school_id=payment.schoolId. A future explicit attribution/school composite would close that database gap without disallowing legitimate NULL recipients.

RISK: Valid same-school non-PARTNER rows must not be cleared or forced to have a Partner recipient. Missing attribution IDs can block standalone addition; foreign-school attribution IDs can block future school binding. Removing standalone admits orphan metadata and permits deletion when composite is skipped; removing partner composite admits wrong Partner matching. Parent school/partner reassignment can affect immutable ledger ownership; audit historical rows without treating ended attribution status as invalid.

All relevant FKs use MATCH SIMPLE, are non-deferrable and have ON UPDATE NO ACTION. Current attribution composite defaults to ON DELETE NO ACTION while historical SQL specifies RESTRICT; current standalone remains RESTRICT and protects every non-NULL attribution ID, including skipped composite rows. NO ACTION and RESTRICT should not be silently treated as identical declarations or changed during this stage.
