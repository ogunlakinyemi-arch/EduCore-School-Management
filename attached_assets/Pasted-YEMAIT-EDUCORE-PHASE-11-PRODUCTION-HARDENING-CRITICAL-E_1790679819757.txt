YEMAIT EDUCORE — PHASE 11: PRODUCTION HARDENING

CRITICAL EXECUTION RULE

This phase is a production-readiness hardening phase, NOT a production deployment.

Work in DEVELOPMENT and disposable test environments only.

ABSOLUTELY DO NOT:

- Publish
- Deploy
- Modify the production database
- Run SQL against production
- Run migrations against production
- Modify production users
- Modify production authentication settings
- Modify production secrets
- Modify production environment variables
- Change production payment configuration
- Change production SMS/email/push configuration
- Create production data
- Delete production data
- Trigger production webhooks
- Send real production notifications
- Make irreversible production changes

Production must remain untouched throughout this phase.

The purpose is to make the existing development codebase and deployment configuration ready for a later controlled production release.

4. AUTHENTICATION HARDENING

Review Clerk authentication integration.

Verify:

- Unauthenticated requests return 401.
- Authenticated users receive only authorized resources.
- Session identity comes from the trusted authentication layer.
- User IDs are not trusted from arbitrary request bodies.
- Role information cannot be escalated through frontend input.
- School scope cannot be changed by modifying request parameters.
- Logout behavior is correct.
- Expired sessions are rejected.
- Protected API routes are consistently protected.
- Frontend route protection does not replace backend authorization.

Check for:

- Missing auth middleware
- Inconsistent auth checks
- Role confusion
- Session caching problems
- Stale authorization state
- Unsafe development bypasses
- Setup/bootstrap mechanisms accidentally available in production

Any development-only authentication bypass must be clearly gated and impossible to activate accidentally in production.

26. MIGRATION HARDENING

This is a critical area.

The development migration ledger has previously been reported as potentially behind the actual development schema.

Do NOT blindly reconcile it.

Instead:

1. Inspect all migrations.
2. Determine actual schema state.
3. Determine migration-ledger state.
4. Create a disposable PostgreSQL database.
5. Replay all migrations from the beginning.
6. Verify the resulting schema.
7. Compare it against the expected development schema.
8. Identify drift.
9. Determine whether drift is:
   - expected;
   - historical;
   - dangerous;
   - deployment-blocking.

If a migration problem exists:

- Fix it in development.
- Test clean replay.
- Test replay against a representative disposable copy.
- Do NOT execute against production.

Do not delete historical migrations merely to make the migration runner pass.
