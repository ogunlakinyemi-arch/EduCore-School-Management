---

1. PHASE 8 OBJECTIVE

Build a centralized, secure Communication and Notification system for Yemait EduCore.

The system must support:

1. In-app notifications
2. SMS notifications
3. Email notifications
4. Push-notification readiness for the future PWA/mobile application
5. Notification templates
6. Notification preferences
7. Notification history
8. Delivery status tracking
9. Bulk school messaging
10. Targeted messaging
11. Automated notifications generated by existing system events
12. Communication audit logging

WhatsApp Business must NOT be implemented.

Telegram may remain a future/optional integration and must not be required for Phase 8.

SMS remains an important communication channel because many Nigerian parents may not have email access.

---

2. ARCHITECTURE

Do not hard-code SMS/email logic into individual modules.

Create or extend a centralized notification/event architecture.

Preferred flow:

EVENT
→ Notification Service
→ Notification Record
→ Channel Dispatcher
→ SMS / Email / In-App / Push
→ Delivery Status
→ Audit Log

Examples:

Attendance event
→ Notification Service
→ Parent notification
→ SMS + In-App

Verified payment
→ Notification Service
→ Parent notification
→ SMS + Email + In-App

New assignment
→ Notification Service
→ Student/Parent
→ In-App + Push when available

School announcement
→ Communication Service
→ Target recipients
→ Selected communication channels

Reuse existing backend patterns, database conventions, authentication, validation, audit logging, React Query, API conventions and UI components.

Do not introduce an unnecessary new framework.

---

3. COMMUNICATION CHANNELS

A. IN-APP NOTIFICATIONS

Implement a notification centre for authenticated users.

Users should be able to:

- View unread notification count
- Open notification centre
- View notifications
- Mark notification as read
- Mark all as read
- View notification timestamp
- View notification category
- Open relevant record/page where appropriate

Notification categories should include examples such as:

- Attendance
- Academic
- Assignment
- Finance
- Payment
- Announcement
- Account
- System
- Subscription
- Partner
- Security

Notifications must remain tenant-safe.

---

4. SMS

Create an SMS provider abstraction.

Do NOT hard-code one provider throughout the application.

Use an interface/service structure that can support a provider such as Termii or another Nigerian SMS provider.

The implementation should support:

- Send SMS
- Provider message ID
- Delivery status
- Failed status
- Error information
- Retry handling
- Idempotency
- Provider response logging without exposing secrets

Provider credentials must come from environment variables/secrets.

Never store provider API keys in source code.

Create a development/test adapter so automated tests do not send real SMS.

Do not claim real SMS delivery has been verified unless real provider credentials and a real test delivery are actually performed.

---

5. EMAIL

Create an email provider abstraction.

Support:

- Account invitations
- Password/account notifications where applicable
- School announcements
- Payment notifications
- Receipts
- Academic notifications
- Attendance notifications
- System notifications

Provider credentials must use environment secrets.

Create a development/test email adapter.

Do not claim real external email delivery is configured unless credentials and actual delivery are verified.

---

6. PUSH NOTIFICATION READINESS

Prepare the backend architecture for future PWA/mobile push notifications.

Create a safe device/subscription model capable of storing a user's push subscription/device reference.

Requirements:

- User-bound
- Tenant-aware
- Revocable
- Multiple devices allowed
- No unnecessary personal device information
- Secure endpoint handling
- No hard-coded push provider credentials

Do not require a native mobile application for Phase 8.

Do not break the existing web application.

The architecture should allow the future Yemait EduCore PWA/mobile app to subscribe to push notifications without redesigning the notification system.

---

7. NOTIFICATION PREFERENCES

Allow appropriate users to manage notification preferences.

Examples:

- SMS enabled/disabled
- Email enabled/disabled
- In-app enabled
- Push enabled when available

Preferences must respect mandatory system notifications.

For example, security/account notifications may not be suppressible where required.

Preferences must be tenant/user scoped.

A user's preference in School A must not affect another user or another school.

10. SCHOOL ANNOUNCEMENTS

School Admin should be able to send communications to authorized groups.

Targeting options:

- Entire school
- Parents
- Students
- Teachers/staff
- Specific class
- Specific section
- Specific students
- Specific parents where appropriate

Provide recipient counts before sending.

Prevent cross-school targeting.

Do not allow a School Admin from School A to target School B.

---

11. ROLE PERMISSIONS

PLATFORM OWNER

Platform Owner communication permissions must remain platform-level.

Do not automatically give Platform Owner school operational communication privileges merely because they can view school information.

Platform Owner should not be able to send ordinary school announcements to a school's parents/teachers unless an explicitly authorized platform communication function already exists.

Do not use Platform Owner status as a shortcut around school-level authorization.

SCHOOL ADMIN

Can manage communication for their own school.

Can:

- Create announcements
- Target authorized school groups
- View school communication history
- Manage appropriate templates
- View delivery results

Cannot access another school's communication data.

TEACHER

Can only communicate within authorized school/class/subject scope.

Do not allow unrestricted school-wide messaging unless explicitly authorized by the existing role model.

ACCOUNTANT

Can send/view finance-related communication within their authorized school scope.

Cannot access another school's finance communication.

PARENT

Can receive relevant notifications.

Parent communication access must be limited to their linked children and authorized school.

STUDENT

Can receive notifications relevant to their own account, school, class and academic records.

PARTNER

Only partner-related notifications should be visible unless existing authorization explicitly provides more.

Partner communication must not expose school-private information.

13. DELIVERY STATUS

Support statuses such as:

- QUEUED
- PROCESSING
- SENT
- DELIVERED
- READ
- FAILED
- CANCELLED

Use statuses appropriate to each channel.

Do not pretend an SMS is delivered merely because the provider API accepted it.

Provider acknowledgement and actual delivery should remain distinguishable.

---

14. RETRIES AND IDEMPOTENCY

Implement safe retry handling.

Requirements:

- Prevent duplicate notifications
- Prevent duplicate payment notifications
- Prevent duplicate invitation notifications
- Support retry for temporary provider failures
- Do not endlessly retry permanent failures
- Use idempotency keys where appropriate

The same underlying event must not accidentally send multiple identical SMS messages because of repeated API requests, webhook retries, or page refreshes.

---

15. SECURITY

All communication endpoints must enforce backend authorization.

Verify:

- Authentication
- Role authorization
- School/tenant authorization
- Parent-child relationship
- Teacher/class authorization
- Student ownership
- Partner attribution
- Platform-level restrictions

Never rely solely on frontend-hidden buttons.

A user manually calling an API must receive an authorization error if they do not have permission.

Prevent:

- Cross-school messaging
- Cross-school notification reads
- Unauthorized recipient injection
- IDOR
- Bulk-message abuse
- Provider credential exposure
- Message spoofing
- Duplicate sends

---

16. RATE LIMITING

Protect communication endpoints against abuse.

Apply appropriate limits to:

- Bulk SMS
- Bulk email
- Announcement creation
- Notification retries
- Push registration
- Verification/account messages

Do not make limits so restrictive that normal school operations fail.
