1. Device Activation Officer role

Create/use a dedicated restricted internal role:

"DEVICE_ACTIVATION_OFFICER"

This is a Yemait Technologies internal employee role.

It is NOT:

- a School Staff membership;
- a Platform Owner account.

The officer must have a restricted dashboard and only the permissions necessary for NFC/device activation.

The officer should be able to:

- view authorized schools/devices needed for activation;
- link/activate NFC cards to students;
- view the minimum student information required for activation;
- view student passport/photo needed for e-ID;
- preview/generate the student's e-ID;
- access activation history/audit information.

The officer must NOT receive the full Platform Owner dashboard or unrestricted school administration access.

Do not weaken existing RBAC or tenant isolation.

2. NFC activation workflow

Implement the workflow:

School
→ NFC Device
→ Student
→ NFC Card
→ Assign
→ Updated E-ID
→ Print

School

Allow the authorized Device Activation Officer to select an authorized school.

Only schools the logged-in officer is permitted to access may be returned.

NFC Device

After selecting the school:

- Load NFC devices already linked to that school.
- If there is only one active device, automatically select it.
- If there are multiple active devices, allow the officer to select the device.
- Automatically populate the device's serial/hardware UID.
- Hardware UID must be read-only.
- Do not require manual Hardware UID entry.

The device serial/hardware UID identifies the physical NFC hardware device.

Never allow a device belonging to School A to be used for activation against School B.

The backend must independently verify the device-school relationship.

Student

Replace manual Student ID entry with a searchable Student dropdown.

Only students belonging to the selected school may appear.

Display useful information such as:

- Student name
- Student ID
- Class/section

The officer selects the student.

The system obtains the actual student ID from the selected student record.

Do not require manual Student ID entry.

The backend must independently verify that the selected student belongs to the selected school.

NFC Card Number

The officer enters or scans the physical NFC card number.

Keep the card number separate from the Hardware UID.

Hardware UID = NFC device identifier.

Card number = physical student NFC card identifier.

Validate server-side that:

- the card is valid according to the existing NFC implementation;
- the card is not already actively assigned to another student;
- the selected student belongs to the selected school;
- the selected device belongs to the selected school;
- the authorized officer can perform the operation.

Do not silently overwrite an existing active card assignment.

Use the existing replacement/deactivation process if one exists.

3. Secure server-side assignment

Do not rely on frontend validation.

When the assignment is submitted, the backend must independently validate:

1. Current user authorization.
2. Officer role.
3. School access.
4. Device belongs to selected school.
5. Student belongs to selected school.
6. Card is available.
7. No conflicting active assignment exists.

Reject cross-school attempts.

Examples that MUST fail:

- School A device + School B student.
- School A student + School B device.
- Card already actively assigned to another student.
- Unauthorized officer attempting activation.

Preserve existing audit and activation history.

Do not remove existing security constraints.

If the student photo is later changed, newly generated E-ID cards must use the latest persisted photo.
