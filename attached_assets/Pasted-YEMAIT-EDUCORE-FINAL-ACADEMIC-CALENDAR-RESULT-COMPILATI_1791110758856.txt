YEMAIT EDUCORE — FINAL ACADEMIC CALENDAR, RESULT COMPILATION, FEES AND SOFTWARE HARDENING

Work only in Development.

Do not publish to Production.

Do not reset, reseed, truncate, delete or rewrite existing data.

Do not rebuild already-working modules.

The objective is to permanently resolve the remaining software gaps and add the required Academic Session/Term management and multi-subject result compilation workflow.

---

1. SCHOOL ADMIN — ACADEMIC SESSION AND TERM MANAGEMENT

New required functionality

School Admin must be able to create and manage the school's academic sessions and their terms.

The system must NOT assume that every school uses the same term dates.

The school should be able to configure its own academic calendar.

---

2. ACADEMIC SESSION

School Admin should have:

School Admin → Academic Calendar → Academic Sessions

The School Admin should be able to create a session such as:

2026/2027

The session should contain:

- Session name
- Start date
- End date
- Status
- Created by
- Created date

Example:

2026/2027

Start:

September 2026

End:

July 2027

The exact dates should be configurable.

---

3. TERMS WITHIN AN ACADEMIC SESSION

Each academic session must contain its own terms.

For example:

2026/2027

First Term

Start:

September 2026

End:

December 2026

Second Term

Start:

January 2027

End:

April 2027

Third Term

Start:

April/May 2027

End:

July 2027

The School Admin must be able to choose the exact dates.

Do not hard-code the dates.

---

4. NEXT ACADEMIC SESSION

After 2026/2027:

2027/2028

First Term may start:

September 2027

The system must treat this as a completely separate academic session.

Do not allow:

2027/2028 First Term

to accidentally share the same term record as:

2026/2027 First Term.

Every term must belong to exactly one academic session.

---

5. TERM CREATION WORKFLOW

School Admin:

2026/2027

- First Term
- Second Term
- Third Term

Enter:

- Start date
- End date

Then save.

---

6. TERM VALIDATION

The system must validate academic periods.

Prevent:

- duplicate terms inside the same session
- two First Terms in one session
- invalid start/end dates
- end date before start date
- overlapping terms unless explicitly permitted
- a term belonging to multiple sessions
- fees being assigned to a nonexistent term
- results being submitted to a nonexistent term

If a school intentionally needs overlapping dates, require an explicit authorized confirmation rather than silently accepting the overlap.

---

7. SESSION/TERM STATUS

Use appropriate statuses such as:

- Draft
- Active
- Closed

If the existing system already has equivalent statuses, reuse them.

Only an active/valid academic period should be available for normal current academic operations.

Historical periods must remain accessible for:

- results
- report cards
- attendance
- fees
- payments
- academic records
- audits

Do not delete historical sessions or terms merely because they have ended.

---

8. ACADEMIC PERIOD USED ACROSS THE PLATFORM

Where applicable, use the configured School Academic Calendar for:

- Fees
- Payments

9. RESULT COMPILATION — MULTIPLE SUBJECT TEACHERS

Critical requirement

The system must correctly compile results submitted by different subject teachers into one consolidated student result.

Example:

A student is in:

JSS1 A

Academic session:

2026/2027

Term:

First Term

The student has several subjects.

Mathematics Teacher

Mathematics teacher submits:

Mathematics — 78

English Teacher

English teacher submits:

English — 82

Basic Science Teacher

Basic Science teacher submits:

Basic Science — 75

Other subject teachers submit their respective subjects.

The system must NOT create separate unrelated results for each teacher.

It must compile all valid subject results into one student's term result.

---

10. RESULT IDENTITY

Every subject result must be uniquely associated with:

School + Student + Academic Session + Term + Class/Section + Subject

This is critical.

For example:

School A + Student 001 + 2026/2027 + First Term + JSS1 A + Mathematics

is one subject result.

And:

School A + Student 001 + 2026/2027 + First Term + JSS1 A + English

is another subject result.

Both belong to the same consolidated student result.

---

11. SUBJECT TEACHER SUBMISSION

Each subject teacher should only submit results for the subjects/classes they are authorized to teach.

Example:

Mathematics Teacher:

JSS1 A Mathematics

can submit Mathematics results.

They should NOT be able to submit:

JSS1 A English

unless they are also authorized to teach English.

---

12. SUBJECT RESULT STATUS

Each subject submission should have an appropriate status.

For example:

- Draft
- Submitted
- Returned
- Resubmitted
- Approved

Reuse the existing result workflow/status model if already implemented.

Do not create a duplicate status system unnecessarily.

---

13. TEACHER SUBMITS MATHEMATICS

Mathematics teacher completes all required students.

Then:

Submit Mathematics Results

2026/2027 → First Term → JSS1 A → Mathematics

The teacher's submission should not publish the student's overall result.

14. ENGLISH TEACHER SUBMITS ENGLISH

English teacher later submits:

2026/2027 → First Term → JSS1 A → English

Do NOT replace Mathematics.

Do NOT create another independent overall result.

17. MISSING SUBJECTS

The system must distinguish between:

Teacher has not submitted

and:

Student has no subject

These are NOT the same.

- blank score treated as zero

unless the existing school's grading policy explicitly says so.

---

18. RESULT COMPLETENESS

Before School Admin publishes the overall class/student results, the system should be able to determine whether all expected subjects have been submitted.

Expected subjects should be derived from the student's:

- class
- section
- subject enrollment/curriculum
- assigned subjects

Not merely from whichever teachers happened to submit results.

Example:

Expected:

1. Mathematics
2. English
3. Basic Science
4. Social Studies
5. Computer Studies

Submitted:

1. Mathematics
2. English
3. Basic Science

The system should show:

2 subjects awaiting submission

and identify them.

19. SCHOOL ADMIN REVIEW OPTIONS

School Admin should be able to:

- review submitted subject results
- identify missing subjects
- return a subject result for correction
- approve subject results where the existing permission model permits
- compile the consolidated result
- publish only when required conditions are satisfied

Do not allow the School Admin to accidentally alter teacher-owned raw scores unless the existing workflow explicitly grants that authority.

↓

↓

↓

School Admin → Review Consolidated Result

↓

School Admin → Approve

↓

School Admin → Publish

↓

Do not allow a single subject teacher to bypass this workflow.
