YEMAIT EDUCORE — PRE-PHASE 7 ARCHITECTURE & USER MANAGEMENT CORRECTION

IMPORTANT — READ BEFORE MAKING CHANGES

I am currently at Phase 7 — Finance of the Yemait EduCore development.

Before continuing Phase 7 Finance, I need you to correct and restructure the existing Owner Admin, Partner, School Administrator, user-management, onboarding, role/permission, tenant-isolation, NFC, and school-data-import architecture.

This is an architecture correction before continuing Phase 7, not a request to rebuild the entire platform.

DO NOT:

- Restart the project.
- Rebuild completed phases unnecessarily.
- Delete existing production/test data.
- Remove completed functionality.
- Break existing authentication.
- Break existing finance functionality already implemented.
- Replace working features unnecessarily.

FIRST:

1. Inspect the entire existing Yemait EduCore codebase.
2. Inspect the current database schema.
3. Inspect the existing authentication implementation.
4. Inspect the existing Owner Admin portal.
5. Inspect the current Partner implementation.
6. Inspect the current School Administrator/user-management workflow.
7. Inspect existing roles and permissions.
8. Inspect existing NFC device/card functionality.
9. Inspect existing Phase 7 Finance work.
10. Identify what needs to be modified versus what can be preserved.

Then implement the architecture below using the existing system wherever possible.

After implementation, perform a complete regression and security test.

---

1. YEMAIT EDUCORE PLATFORM HIERARCHY

Yemait EduCore must operate as a secure multi-tenant school management SaaS platform.

The hierarchy should be:

Yemait Technologies
│
├── Platform Owner / Owner Admin
│   └── Full platform-wide administration
│
├── Partners
│   ├── Partner Owner/Admin
│   └── Partner Staff/Admin
│
└── Schools
└── School Administrator
├── Teachers
├── Accountants
├── Staff
├── Parents
└── Students

The Platform Owner has platform-wide visibility and control.

Partners have restricted partner-scoped visibility.

Each school is a separate tenant.

School users can only access data belonging to their authorized school.

---

2. PLATFORM OWNER ADMIN

The existing Owner Admin portal must become the central platform administration portal.

The Platform Owner should be able to:

- Create schools
- View all schools
- View school status
- View school administrators
- View students across schools
- View parents
- View teachers
- View staff
- View accountants
- View student counts
- View school activity
- View platform-wide reports
- View platform-wide finance information where authorized
- Manage partners
- View partner information
- View schools referred by each partner
- View partner commissions
- Manage NFC devices
- Assign NFC devices to schools
- Unassign/reassign NFC devices
- View NFC device status
- Link NFC cards to students
- View NFC card assignments
- Manage platform-level settings
- View audit logs
- Perform authorized platform-level administrative actions

The Platform Owner has the highest level of access.

However, the Platform Owner should NOT be responsible for manually entering every student's, parent's, teacher's, or staff's information.

---

3. OWNER ADMIN SCHOOL CREATION

When the Platform Owner creates a school, the Owner Admin should NOT create the School Administrator's password.

The workflow must be:

Platform Owner
→ Create School
→ Enter school information
→ Enter School Administrator name/email
→ Assign role: School Administrator
→ Send invitation

The School Administrator receives an invitation email.

The administrator opens the secure invitation link and creates their own password.

The Platform Owner must NEVER see or create the administrator's plaintext password.

Use the existing authentication provider securely.

The invitation should:

- Use a secure non-guessable token.
- Have an expiration period.
- Be usable only as intended.
- Become invalid after successful activation where appropriate.

---

4. SCHOOL ADMINISTRATOR

Once the School Administrator activates the account, they become the administrator of that school's tenant.

The School Administrator should manage their own school.

They should be able to create/invite:

- Teachers
- Accountants
- Other staff
- Parents
- Students
- Other authorized school roles

The School Administrator should NOT need the Platform Owner to manually create operational users.

---

5. SCHOOL USER INVITATION WORKFLOW

The School Administrator should use the same secure invitation workflow.

Example:

School Administrator
→ Add Teacher
→ Enter teacher information/email
→ Assign role
→ Send invitation

Teacher receives invitation.

Teacher creates their own password.

The same principle applies to:

- Accountants
- Staff
- Parents
- Other invited users

The School Administrator must NEVER see another user's plaintext password.

---

6. STUDENT MANAGEMENT

The School Administrator should create and manage student records for their school.

The Platform Owner should NOT manually create every student for schools.

Student records must belong to the school's tenant.

The Platform Owner can view students across schools because of platform-wide permissions.

Partners cannot view individual student records.

School Administrators can manage only students belonging to their school.

---

7. PARENT MANAGEMENT

The School Administrator should be able to create/invite parents.

A parent may have multiple children.

Example:

Parent Account
→ Child A
→ Child B
→ Child C

Parents should only see children associated with their account.

The School Administrator manages parent/student relationships within their school.

The Platform Owner can view this information according to Owner permissions.

Partners cannot access private parent information.

8. BULK FILE IMPORT — IMPORTANT

Schools may already have their student, parent, teacher, or staff information stored electronically.

The School Administrator must therefore be able to upload existing files instead of manually entering hundreds or thousands of records one by one.

Support at minimum:

- Excel (.xlsx)
- CSV (.csv)
- PDF (.pdf) where technically reliable

This should be a core School Administrator feature.

Examples:

School Administrator
→ Students
→ Import Students

School Administrator
→ Parents
→ Import Parents

School Administrator
→ Teachers
→ Import Teachers

School Administrator
→ Staff
→ Import Staff

9. STUDENT BULK IMPORT

For Excel/CSV student files, provide a column-mapping workflow.

Do NOT assume every school uses the same column names.

Example uploaded file:

First Name | Surname | Admission No | Class | Gender | DOB | Parent Phone

Map to:

First Name → first_name
Surname → last_name
Admission No → admission_number
Class → class
Gender → gender
DOB → date_of_birth
Parent Phone → parent_phone

The administrator must be able to map columns before importing.

---

10. PDF IMPORT

Schools may have student lists in PDF.

Where the PDF contains selectable/tabular text:

1. Upload PDF.
2. Extract readable table/text data.
3. Show detected records.
4. Allow column/field mapping.
5. Validate records.
6. Show warnings/errors.
7. Require administrator confirmation.
8. Import only after confirmation.

If a PDF is scanned/image-based and reliable extraction is not possible, do NOT silently create incorrect records.

Instead display an appropriate message and recommend Excel/CSV or the provided template.

If OCR already exists in the application, it may be used, but OCR results must still pass through preview and validation before being saved.

---

11. IMPORT PREVIEW

Never immediately create records from an uploaded file.

Show an import preview first.

Example:

IMPORT PREVIEW

File: Students_2026.xlsx

Records detected: 845
Valid: 832
Warnings: 8
Errors: 5

Display each problematic row and explain the issue.

The administrator must be able to resolve or exclude problematic records before final confirmation.

---

12. DUPLICATE DETECTION

Detect potential duplicates before creating records.

Use appropriate identifiers such as:

- Admission number
- Student ID
- Name + date of birth where appropriate
- Other school-specific identifiers

Do not create duplicate records simply because the same student appears twice.

Allow:

- Skip duplicate
- Review duplicate
- Update existing record where authorized
- Import as new only after explicit confirmation

Never overwrite existing data without explicit confirmation.

20. IMPORT SECURITY

Uploaded files and imported records must belong to the authenticated School Administrator's school.

A School Administrator from School A must never be able to import data into School B.

The backend must determine the school/tenant from the authenticated user's authorization.

Do NOT trust school_id or tenant_id supplied by the uploaded file.
