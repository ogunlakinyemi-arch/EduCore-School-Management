Fix the invitation system for Yemait EduCore. Do not publish, deploy to production, change production data, or modify production configuration.

The current development problems are:

1. Partner invitation links open a 404 Page Not Found.
2. School Admin invitation links open a 404 Page Not Found.
3. Company Employee invitation links open a 404 Page Not Found.
4. Other invited users are also affected by the invitation-link 404.
5. Partner → Resend currently shows:
   "Resend failed — The partner invitation was not finalized locally. Clerk did not confirm whether the request was accepted; check before retrying."
6. Platform Owner must be able to resend School Administrator invitations.
7. The School invitation currently exposes operational/invitation status information too early.
8. A school must NOT appear operational merely because the Platform Owner entered the administrator's information or generated an invitation.
9. The school's operational status should change only after the invited School Administrator actually completes registration through the invitation link and the backend successfully links the Clerk account to the school administrator role.

Use one canonical application route:

"/accept-invitation"

It must be publicly reachable before the recipient has an application account.

It must NOT be blocked by:

- authenticated-only guards
- existing role guards
- school membership guards
- Platform Owner guards
- Parent/Student/Partner dashboard guards.

It must correctly receive and preserve the Clerk invitation ticket/query parameters.

Never display a generic 404 for a valid invitation URL.

3. HANDLE CLERK INVITATION TICKETS CORRECTLY

Do not invent or expose invitation tokens.

Use the actual Clerk invitation mechanism.

When the recipient opens the emailed link:

1. Preserve the Clerk invitation ticket.
2. Preserve the server-side invitation reference where applicable.
3. Allow the recipient to complete registration/sign-in.
4. After Clerk confirms the identity, send the authenticated identity to the backend.
5. Backend resolves the invitation from its own database/server-side invitation record.
6. Backend verifies that the authenticated Clerk email/account corresponds to the intended invitation.
7. Backend links the account to the intended role and school/company/partner scope.
8. Mark the invitation accepted only after successful backend linking.

Do NOT determine the final role from an arbitrary URL parameter.

The backend invitation record must be authoritative.

5. PARTNER RESEND MUST WORK

Fix the exact error shown in the screenshot:

«"Resend failed
The partner invitation was not finalized locally.
Clerk did not confirm whether the request was accepted; check before retrying."»

The current implementation must not leave the application in an ambiguous state where Clerk may have accepted the request but the local database did not finalize it.

Implement a safe resend operation with proper idempotency.

Required behavior:

- Only an active Platform Owner can resend Partner invitations.
- Verify the Partner is still Pending.
- Verify there is no already-linked active Partner account.
- If an existing invitation is expired/invalid, safely create a replacement invitation.
- If the previous Clerk request may have succeeded but local finalization failed, reconcile the state before creating another invitation.
- Never create duplicate active Partner memberships.
- Never accidentally revoke the only usable invitation before a replacement has been successfully created.
- Store the new invitation reference correctly.
- Audit the resend.
- Return a clear success/failure response.

If Clerk cannot confirm the request, do NOT pretend that the resend succeeded.

Instead, safely reconcile the invitation state and provide a meaningful error.

7. SCHOOL OPERATIONAL STATUS — IMPORTANT

Change the current school onboarding status behavior.

When the Platform Owner enters:

- School name
- School information
- First administrator name
- First administrator email

the school is created, but the school must NOT be considered operational/activated merely because the invitation was created.

Do NOT display an "Operational" status as if the administrator has completed onboarding.

The state should clearly distinguish:

- School created
- Invitation pending
- Registration completed
- Active/Operational

The important rule is:

Creating the school or sending the invitation does NOT make the school operational.

The school becomes operational/active only after:

1. The invited School Administrator clicks the invitation.
2. The administrator successfully completes Clerk registration/sign-in.
3. Backend verifies the Clerk identity.
4. Backend successfully links the account to the intended School Admin role and school.
5. The onboarding/activation transaction succeeds.

Only then should the Platform Owner see the school as operational/active.
