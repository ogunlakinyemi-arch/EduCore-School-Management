7. RELATIONSHIP #1 — PLATFORM DEVICES → SCHOOL CLASSES

Audit:

platform_devices.school_id
platform_devices.school_class_id

Historical design:

(platform_devices.school_class_id, platform_devices.school_id)
→
(school_classes.id, school_classes.school_id)

The historical relationship was created in migration 0009 and was NOT VALID.

Current source also contains a standalone:

platform_devices.school_class_id
→
school_classes.id

Read-only audit:

A. Total platform_devices rows.

B. Count rows where:

- school_id IS NULL
- school_class_id IS NULL
- both are populated

C. Orphan class references:
platform_devices.school_class_id has no matching school_classes.id.

D. Cross-school mismatches:

platform_devices.school_id
<>
school_classes.school_id

when both are non-NULL.

E. Calculate historical composite compatibility:

For each row, determine whether:

(school_class_id, school_id)
matches
(school_classes.id, school_classes.school_id)

Remember PostgreSQL MATCH SIMPLE behavior:

If either referencing column is NULL, the composite FK does not require a parent match.

Therefore report separately:

- valid composite-reference rows
- rows skipped because of NULL
- rows that would violate the historical composite rule

DO NOT validate the actual constraint.
