1. OBJECTIVE

Resolve and document the migration-ledger uncertainty identified during Phase 11 Production Hardening.

Current findings:

- 31 checked-in migrations replay successfully on an empty disposable PostgreSQL database.
- The migration runner is idempotent on a second run.
- A disposable backup/restore preserved schema and migration ledger.
- However, a disposable clone of the current development schema contains only five migration-ledger entries.
- Replaying the migration runner against that cloned schema fails at an already-existing object in migration "0005".
- The development migration ledger was intentionally left untouched.

The objective is NOT to force the migration runner to succeed by deleting or hiding information.

The objective is to determine the safest, evidence-based way to reconcile:

1. Checked-in migrations
2. Migration ledger
3. Actual development schema
4. A representative database containing realistic development data

3. CLASSIFY THE MIGRATION DRIFT

Determine which situation actually exists.

Case A — Ledger is incomplete but schema matches migrations

The database already contains the objects created by earlier migrations, but the ledger does not record those migrations.

Case B — Schema differs from migration history

The schema contains changes not represented by the checked-in migrations.

Case C — Object exists but differs from expected migration definition

For example:

- Different constraint
- Different index
- Different column
- Different data type
- Different default
- Different foreign key
- Different function
- Different trigger

Case D — Development schema contains manually applied changes

Identify exactly what they are.

Case E — Migration itself is not safely idempotent

Identify the migration and exact statement.

Do not assume Case A.

5. DETERMINE THE SAFE RECONCILIATION STRATEGY

Only after inspection determine whether reconciliation should use:

Strategy A — Ledger-only reconciliation

If the actual schema demonstrably matches the historical migrations, the migration ledger may be safely advanced to reflect already-applied migrations.

However, do NOT perform this automatically.

Verify object equivalence first.

Strategy B — Idempotent migration correction

If migrations contain unsafe statements such as:

- CREATE TABLE without existence checks
- CREATE INDEX without appropriate checks
- CREATE FUNCTION without safe replacement logic
- ADD CONSTRAINT without checking existing equivalent constraints

make the migration/reconciliation logic safe where appropriate.

Do not blindly rewrite historical migrations if doing so changes their meaning.

Strategy C — Baseline migration

If the database represents a legitimate existing schema that cannot safely be reconstructed through historical migrations, design a reviewed baseline strategy.

Do not delete historical migrations.

Do not create a fake ledger state simply to make deployment appear successful.

Strategy D — New reconciliation migration

If the schema needs actual changes, create a new migration rather than modifying historical migration meaning.

Use this only when evidence supports it.

6. DO NOT DESTROY MIGRATION HISTORY

Never:

- Delete old migrations.
- Rename old migration IDs just to bypass errors.
- Delete migration ledger rows blindly.
- Mark migrations as applied without verifying their effects.
- Drop production-like objects just to replay migrations.
- Recreate the database merely to hide drift.

The final migration history must remain understandable to another developer.
