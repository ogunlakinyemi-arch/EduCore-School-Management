YEMAIT EDUCORE — MASTER DEVELOPMENT PROMPT

You are working on Yemait EduCore, a multi-school SaaS school-management platform owned by Yemait Technologies Limited.

The existing application is already substantially developed. Do not rebuild, replace, simplify, or remove existing functionality. Extend the existing architecture safely.

1. CORE RULE — PRESERVE THE EXISTING SYSTEM

Before making changes:

1. Inspect the existing codebase, database schema, migrations, routes, components, authentication, RBAC, and existing workflows.
2. Preserve all existing working functionality.
3. Preserve all existing user roles and permissions.
4. Preserve existing Clerk authentication and invitation workflows.
5. Preserve school/tenant isolation.
6. Preserve existing NFC/device architecture.
7. Preserve existing academic, attendance, finance, communication, library, operations, reporting, transport, payroll, subscription, partner, and notification modules.
8. Do not create duplicate systems where an existing module already performs the required function.
9. Reuse existing tables, APIs, components, services, and authorization logic wherever appropriate.
10. Do not perform destructive database changes.
11. Do not reset or replace the existing database.
12. Do not change Production.
13. Development changes and migrations must be safe, reversible, and fully tested.
14. Do not create unnecessary migrations if the existing schema already supports the required feature.

3. SCHOOL REGISTRATION

Keep the existing School Registration workflow.

When the Platform Owner creates a school:

- Platform Owner enters the required school information.
- Platform Owner must NOT manually enter the School Registration Number.

- It must be unique across the platform.
- It must remain permanently associated with that school.
- Existing schools must not receive new registration numbers.

Preserve the existing Owner → School Admin relationship.

4. SCHOOL ADMIN USER/PERMISSION ROLE WORKFLOW

IMPORTANT: DO NOT REDESIGN THE EXISTING SCHOOL ADMIN USER/PERMISSION ROLE SECTION.

The existing School Admin User/Permission Role section must remain intact.

The new activation workflow must work on top of the existing users.

When a School Admin wants to send an activation link:

DO NOT make the Admin enter the person's information again.

Instead:

1. Admin selects the user role.
2. System displays existing users belonging to that school and role.
3. Admin selects the existing user from the list/dropdown.
4. System retrieves the existing user's:
   - Name
   - Email
   - User/account ID
   - Existing role
   - Existing account status
5. Admin clicks Send Activation Link.
6. The system sends the activation/invitation link to the existing email.
7. No duplicate user is created.
8. No duplicate student, parent, teacher, or staff record is created.
9. No unnecessary information re-entry is required.

Supported activation selections must include the existing supported roles such as:

- Student
- Parent
- Teacher
- Staff
- Other existing supported school roles

Keep the existing invitation architecture and Clerk authentication.

5. ACCOUNT ACTIVATION

The existing secure invitation workflow must remain.

The School Admin does not create the user's password.

The invited user receives an activation/invitation link.

The user:

1. Opens the link.
2. Completes the required activation process.
3. Creates their own password through the existing authentication flow.
4. Signs in.
5. Is automatically associated with the correct school and role.

Do not expose passwords to School Admin users.

Do not store plaintext passwords.

Keep existing invitation security, expiration, resend, and audit behavior.

7. PARENT REGISTRATION AND CHILD LINKING

Preserve the existing Parent/User/Permission Role architecture.

Parents must be managed as independent user/person records.

When activating a parent:

1. Admin selects Parent.
2. Admin selects an existing parent from the school.
3. System displays existing students in that school.
4. Admin can select one or multiple students.
5. The selected students are linked to the parent.
6. Admin sends the activation link.
7. Parent creates their own password.
8. Parent signs in.
9. Parent automatically sees their linked children.

Existing Parent

If a parent already has an active account:

- Do not create another parent account.
- Do not create another login.
- Do not send another activation link simply because another child is added.
- Add the new child to the parent's existing authorized child relationships.

Pending Parent

If the parent exists but has not completed activation:

- Admin can resend the activation link.
- Do not create a duplicate parent account.

Parent Security

Parent access must always be server-side authorized.

A parent may only access:

- Their own profile
- Their linked children
- Authorized information belonging to those children

A parent must never be able to manipulate an ID or URL to access another school's student or another parent's child.

36. DEVELOPMENT/PUBLISH SAFETY

This is critical.

Do not:

- Change Production database directly.
- Manually bypass Replit's migration generator.
- Delete Production tables.
- Reset Production.
- Drop existing constraints to force migration success.
- Disable security checks.
- Remove existing foreign keys simply to make Publish succeed.
- Invent missing curriculum content to make a test pass.

Before any database migration:

1. Inspect Development schema.
2. Inspect migration ordering.
3. Validate required unique indexes/constraints.
4. Test migration replay.
5. Run relevant automated tests.
6. Run typecheck.
7. Verify no existing records are lost.
8. Report the exact migration plan before attempting any Production action.

If Replit's Publish/schema-diff generator produces an incorrect migration, stop and report the generator problem rather than manually damaging or bypassing the database.
