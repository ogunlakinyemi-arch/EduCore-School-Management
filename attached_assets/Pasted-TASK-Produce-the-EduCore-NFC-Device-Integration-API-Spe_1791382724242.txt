4. Device authorization model

Document how EduCore determines whether a device is allowed to process a card.

The intended relationship is:

NFC Device → School → NFC Card → Student

The device should be linked to a school by an authorized Platform Owner.

A card assigned to a student belongs to that student's school.

A scan should therefore be authorized using the existing backend relationships.

The hardware should NOT independently determine school/student authorization.

5. Scan flow

Document the exact expected flow.

The intended conceptual flow is:

1. NFC card is scanned

→ device reads NFC UID

2. Device sends authenticated request

→ device identity + card UID + required scan information

3. EduCore authenticates the device

→ confirms the device is valid/active

4. EduCore verifies the device's school

→ determines the school associated with the device

5. EduCore verifies the NFC card

→ confirms the card is active and belongs to the same school

6. EduCore resolves the student/person

→ confirms the card is assigned to the appropriate student/person

7. EduCore returns an authorization/result response

→ ALLOW or DENY

8. Device displays the result

ALLOW:

- Green LED
- Success beep

DENY:

- Red LED
- Error/denial beep

Do not implement this flow if the current application differs. Instead document the actual implemented behavior and clearly identify any missing piece.

6. Multiple devices

Confirm how the existing implementation handles multiple NFC devices belonging to the same school.

Expected behavior:

School A

- Device A1
- Device A2

Student card assigned to School A

The card should be usable on both active devices because the card is school-bound, not individually device-bound.

The hardware developer should therefore NOT need to choose a specific device when assigning a student card.

Document whether the current backend already behaves this way.
