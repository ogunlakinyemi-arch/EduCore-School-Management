CRITICAL SAFETY RULES

1. DO NOT modify production.
2. DO NOT run "push", "migrate", "db push", or equivalent against the production database.
3. DO NOT reset the database.
4. DO NOT drop tables.
5. DO NOT truncate data.
6. DO NOT delete production records.
7. DO NOT change production migrations.
8. DO NOT change application code unless a separate confirmed defect is discovered.
9. DO NOT expose database passwords, connection strings, Clerk secrets, API keys, or other secret values.
10. If the environment does not provide a safe disposable database/fork, STOP rather than improvising.
11. Never assume that the Replit database UI and deployed API use the same database.
12. This task is strictly for identifying the database target and rehearsing the migration safely.

PHASE 1 — IDENTIFY THE DEPLOYED API DATABASE TARGET

Inspect the existing deployment configuration and application code.

Determine which environment variable(s) the deployed API uses to connect to PostgreSQL.

Examples may include:

- DATABASE_URL
- DATABASE_URL_UNPOOLED
- PGDATABASE
- PGHOST
- other existing database configuration

Do NOT print the values.

Instead report only:

- variable name
- whether it exists
- whether the application actually reads it
- which server/database initialization code consumes it

Trace the actual code path from application startup to database connection.

Do not rely only on the Replit database UI.

REQUIRED RESULT

Report:

«"The deployed API database target is controlled by: ______"»

Do not provide the secret value.

If the exact target cannot be established safely, STOP PHASE 2 and report why.

- "0000_brainy_moon_knight.sql"

PHASE 3 — CREATE/USE A DISPOSABLE REHEARSAL DATABASE

Only continue if a safe disposable database, fork, branch, or equivalent isolated database is available.

The rehearsal must NOT be the production database.

Prefer this order:

1. Disposable production fork/clone if available.
2. Disposable database containing a representative copy of production schema/data.
3. Fresh disposable PostgreSQL database only if the migration system requires it.

Do not create a production-like copy containing secrets unnecessarily.

If using a production fork, ensure it is isolated and disposable.

---

PHASE 4 — REHEARSE THE MIGRATION

Run the existing migration chain against the disposable database using the project's existing migration mechanism.

Do NOT change the migrations first.

The objective is to determine whether the current migration sequence succeeds in a realistic database state.

Pay particular attention to:

- "nfc_cards"
- existing "(id, school_id)" uniqueness
- "nfc_card_history"
- composite foreign keys
- indexes
- existing historical data
- migration ordering

If the migration fails, capture the exact failing statement and error.

Do not immediately fix it.

First determine whether the failure is:

- migration ordering
- existing data
- missing constraint
- duplicate data
- incompatible schema
- migration-history mismatch
- environment issue
- deployment/publish issue

---

PHASE 5 — IF A FAILURE OCCURS

If the disposable rehearsal fails:

DO NOT modify production.

DO NOT modify the existing migrations immediately.

Report:

Exact failure

The exact migration and database operation that failed.

Root cause

Explain why PostgreSQL rejected it.

Production risk

Explain whether the same condition could affect the real production database.

Minimal safe fix

Describe the smallest forward-only change that would resolve it.

Verification

Explain how the proposed fix would be tested again on the disposable database.

Only after this report should a migration change be considered.

---

PHASE 6 — IF THE REHEARSAL SUCCEEDS

If the complete migration chain succeeds on the disposable database:

- migration chain successfully replayed
- "nfc_cards" constraint verified
- "nfc_card_history" created successfully
- composite foreign key created successfully
- no migration ordering failure observed
- no production database was modified

Then inspect whether the disposable database accurately represents the relevant production schema.

Do NOT publish the migration yet.
