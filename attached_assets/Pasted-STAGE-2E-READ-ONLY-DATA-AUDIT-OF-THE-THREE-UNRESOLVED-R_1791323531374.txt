3. RELATIONSHIP #1 — PLATFORM DEVICE → SCHOOL CLASS

Audit:

platform_devices.school_id
platform_devices.school_class_id

Historical design:

platform_devices(school_class_id, school_id)
→
school_classes(id, school_id)

The historical composite foreign key was created in migration 0009 and was NOT VALID.

Current source also contains a standalone relationship:

platform_devices.school_class_id
→
school_classes.id

We need to determine whether the existing Production TEST DATA would satisfy the historical composite relationship.

Read-only audit:

A. Count:

- total platform_devices
- devices with school_id NULL
- devices with school_class_id NULL
- devices with both values present

B. Detect orphan class references:

- school_class_id points to a school_classes row that does not exist

C. Detect cross-school mismatches:

- platform_devices.school_class_id exists
- school_classes.id exists
- but platform_devices.school_id <> school_classes.school_id

D. Detect:

- school_class_id present while school_id is NULL
- school_id present while school_class_id is NULL

E. Determine whether each existing row would satisfy the historical composite relationship:

(platform_devices.school_class_id, platform_devices.school_id)
→
(school_classes.id, school_classes.school_id)

Remember PostgreSQL MATCH SIMPLE behavior:

- if either referencing value is NULL, the composite FK does not require a parent match
- if both are non-NULL, both values must match

Report:

DEVICE → CLASS

- total rows
- rows satisfying historical composite rule
- rows that would violate historical composite rule
- orphan class references
- cross-school class mismatches
- NULL-related cases
- whether validation of the historical composite FK would currently succeed

Do NOT validate or alter the actual constraint.
Calculate compatibility using read-only queries.
