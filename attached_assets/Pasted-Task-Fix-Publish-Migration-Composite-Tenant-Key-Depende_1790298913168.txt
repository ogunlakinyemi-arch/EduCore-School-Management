Task: Fix Publish Migration Composite Tenant-Key Dependencies Safely

The disposable production fork reports:

"academic_results_class_assignment_school_fk"
references:

"student_class_assignments(id, school_id)"

but PostgreSQL reports:

"there is no unique constraint matching given keys for referenced table "student_class_assignments""

1. Identify the immediate root cause

Inspect the generated migration and confirm that it contains:

"DROP INDEX "student_class_assignments_id_school_unique";"

before creating:

"FOREIGN KEY ("student_class_assignment_id","school_id") REFERENCES "student_class_assignments"("id","school_id")"

This means the migration removes the exact referenced tenant key required by the later composite foreign key.

Do NOT simply remove the foreign key.

Do NOT weaken tenant isolation.

Do NOT replace the composite FK with a single-column FK.

Determine why the schema diff believes the existing tenant key should be dropped.

2. Inspect the actual source schema

Inspect "student_class_assignments" in the schema source and determine:

- primary key
- "school_id"
- existing unique declarations
- generated index names
- whether "(id, school_id)" is intentionally part of the tenant-integrity design
- whether the source schema and actual development/production-fork schema disagree

Because "id" is already the primary key, understand that "(id, school_id)" may appear logically redundant, but PostgreSQL still requires an exact matching UNIQUE/PRIMARY KEY target for a composite FK.

4. Pay special attention to DROP statements

In particular investigate:

A referenced tenant key must not be removed unless an equivalent matching UNIQUE/PRIMARY KEY is created before the FK is added.

5. Determine the intended schema design

The application's tenant-isolation architecture uses composite foreign keys such as:

"(student_class_assignment_id, school_id) → (id, school_id)"

This provides database-level protection against cross-school relationships.

Preserve this architecture.

The safe pattern is:

1. referenced table exists;
2. referenced "(id, school_id)" unique/primary key exists;
3. dependent table exists;
4. dependent composite FK is created;
5. supporting indexes are created.

If an equivalent unique key already exists under another name, do not create unnecessary duplicates. Correct the migration generator/source so it recognizes the existing key.

Do not make arbitrary SQL changes just to make this particular migration pass.
