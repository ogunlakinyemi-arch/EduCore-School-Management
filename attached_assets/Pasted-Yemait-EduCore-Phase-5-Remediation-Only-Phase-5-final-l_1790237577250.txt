BLOCKER 1 — Historical Device Reassignment

Current problem

Device 28 has already recorded School A attendance events.

Attempting to reassign Device 28 to another school currently fails with HTTP 500 because:

"attendance_events_device_school_fk" still references "(28,1)".

The transaction currently rolls back.

This must be fixed without deleting, modifying, or losing historical attendance events.

Required behavior

A device that has historical attendance events MUST be safely reassignable through the authorized Platform Owner/device-management workflow.

Historical events must retain their original school/tenant context.

Example:

- Device 28 records historical events for School A.
- Platform Owner reassigns Device 28 to School B.
- Historical School A events remain School A.
- New Device 28 events are accepted only for School B after reassignment.
- The old School A credential must no longer authorize new events.
- A new secure device credential must be issued/rotated for School B.
- Previous credentials must be invalidated according to the existing security model.
- No historical attendance event may be reassigned to School B.
- No cross-school data leakage may occur.

Important

Do NOT solve this by deleting historical events.

Do NOT change historical events' school IDs.

Do NOT remove the foreign-key constraint merely to make the reassignment pass.

Choose the correct data model/migration so historical attendance preserves its original tenant ownership independently of the device's current assignment.

Possible acceptable architecture:

- Store the historical school/tenant directly on attendance events.
- Keep device's current school assignment separately.
- Historical events reference their original school context.
- Device assignment history may also be retained.

Use the architecture that best fits the existing schema rather than blindly adding duplicate fields.

Required audit

A successful reassignment must create an authenticated audit entry containing at minimum:

- device
- previous school
- new school
- actor
- timestamp
- reassignment action
- credential rotation/invalidation information without exposing secrets

Live verification required

Using Device 28:

1. Confirm existing School A events remain unchanged.
2. Reassign Device 28 from School A to School B.
3. Confirm HTTP success.
4. Confirm a new credential is issued/activated securely.
5. Confirm old credential cannot submit new events.
6. Submit a valid School B event.
7. Confirm the new event belongs to School B.
8. Confirm historical Device 28 events remain School A.
9. Attempt School A event submission using the new School B credential and confirm denial.
10. Verify reassignment audit.
11. Verify no credential/token secret appears in API responses, ordinary logs, or audit metadata.
12. Verify cross-school isolation.

BLOCKER 2 — Discrepancy Resolution

Current problem

Discrepancy 1 exists as:

"SCHOOL_PRESENT_CLASS_MISSING"

It can be viewed but remains OPEN.

There is currently no resolution route or UI workflow.

Required implementation

Implement an authorized discrepancy-resolution workflow.

The workflow must support at minimum:

- OPEN
- RESOLVED
- optionally DISMISSED/WAIVED if appropriate to the existing design

Do not delete discrepancies after resolution.

A resolved discrepancy must retain:

- discrepancy ID
- original type
- student
- school
- related attendance records
- original creation timestamp
- resolver
- resolution timestamp
- resolution reason/comment
- previous status
- new status
- audit record

Authorization

Only appropriately authorized school/platform roles may resolve discrepancies.

At minimum:

- Platform Owner: allowed within authorized scope
- School Admin: allowed for their own school
- Teacher: only if the existing policy explicitly permits it; otherwise deny
- Staff: deny unless explicitly authorized
- Accountant: deny
- Parent: deny
- Student: deny
- Partner: deny

Never allow one school's user to resolve another school's discrepancy.

UI

Add the resolution workflow to the existing discrepancy area.

Do not create a disconnected duplicate attendance system.

The authorized user should be able to:

1. Open discrepancy.
2. Review the related school/class/student attendance information.
3. Choose the permitted resolution.
4. Enter a reason/comment where required.
5. Submit.
6. See the updated status immediately.
7. See resolver and resolution timestamp.
8. See audit history.

Live verification required

BLOCKER 4 — Section Report Filter

Current reports support:

- date/date range
- school
- class
- student
- status
- identification method

But the "section" filter currently does not actually change the result.

Required behavior

Implement a genuine section-level attendance report filter.

The filter must restrict returned attendance records to the selected section.

It must respect:

- school tenancy
- class
- section
- student assignment/history
- attendance event relationships
- appropriate date range

Do not simply filter the frontend display.

The backend query/API must enforce the section filter.

If attendance events do not currently store a section snapshot, use the existing valid class/section relationship carefully so historical records are not incorrectly reassigned when students change sections.

If the correct architecture requires storing historical section context on the attendance event, implement that safely through a migration and preserve existing data.

Live verification required

Create/use test data containing at least two sections.

Verify:

1. No section filter → expected records.
2. Section A → only Section A records.
3. Section B → only Section B records.
4. Section A cannot leak Section B records.
5. School A section filter cannot return School B data.
6. Student/class/date/status filters continue working together with section.
7. Teacher scope remains correctly restricted.
