PHASE 11C — MIGRATION FORENSICS & RELEASE PLAN

PROJECT

Yemait EduCore by Yemait Technologies Limited.

OBJECTIVE

Investigate and document the unresolved migration-history mismatch discovered during Phase 11B.

This phase is FORENSICS AND PLANNING ONLY.

The goal is to determine exactly:

1. Why the development database has only 5 migration-ledger entries while 31 migrations exist in the repository.
2. Why the recorded hashes for the existing entries do not all match the current checked-in migration files.
3. Which migration files correspond to the recorded historical hashes.
4. Whether migrations 0006–0031 were actually applied previously without being recorded.
5. Whether any migration SQL was modified after being applied.
6. What the safest controlled reconciliation sequence should be.
7. What must be verified before any development ledger reconciliation.
8. What must be verified before production deployment.

ABSOLUTE SAFETY RULES

DO NOT:

- modify production
- publish/deploy production
- modify production migrations
- modify the development migration ledger
- update migration hashes
- mark migrations as applied
- delete migration records
- recreate existing production objects
- rewrite migration files merely to make the runner pass
- change application functionality
- perform destructive database operations
- reset the development database
- run unapproved schema changes
- bypass migration validation
- fabricate historical migration evidence

This phase must not alter the application database schema or migration ledger.

Read-only inspection, disposable database experiments, file hashing, SQL parsing, documentation, and test execution are allowed.

If a command could modify the persistent development database, DO NOT run it.

CURRENT KNOWN FACTS

Phase 11B established:

- Repository contains 31 checked-in migrations.
- Development migration ledger contains only 5 rows.
- Normal migration execution against the current development database fails because an object from an earlier migration already exists.
- Two of the five recorded migration hashes differ from the current checked-in SQL.
- One recorded hash matches an older checked-in migration file.
- The original SQL corresponding to the other historical hash has not yet been identified.
- The exact reason migrations 0006–0031 were not recorded has not been verified.
- Synthetic disposable databases successfully demonstrated historical backfills and cross-school protections.
- Synthetic reconciliation can adopt migrations 0006–0031 with an explicit audit label while preserving the original five rows.
- Re-running the reconciled migration sequence on the synthetic database produces no further changes.
- Backup/restore rehearsal passed.
- 595 API/web tests passed.
- Typecheck and builds passed.
- Production remains untouched.

Treat all of these as evidence, not permission to modify the live development database.
