Fix two issues in the existing Partner NFC Card Activation implementation in Yemait EduCore.

This is a Development-only correction. Do not modify Production.

Do not redesign or rebuild the existing Partner, NFC Device, NFC Card, school referral, permission, or subscription systems. Reuse the implementation that was just added.

ISSUE 1 — Platform Owner cannot find Partner NFC Activation permission

The Platform Owner currently has no visible UI section where they can grant a Partner permission to activate/assign NFC cards for that Partner's referred schools.

Required behavior

In the existing Platform Owner → Partner Management area, add a clearly visible permission/control for each Partner:

NFC Card Activation

- Enabled
- Disabled

The Platform Owner must be able to:

- Grant NFC Card Activation permission to a Partner.
- Revoke NFC Card Activation permission.
- See the current permission state.
- See which Partner has NFC activation permission.
- Use the existing audit framework to record grant/revoke actions.

Do not create a separate Partner management page if an existing Partner management page already exists.

The permission must be stored using the existing authorization/permission architecture created for this feature.

Important

Do not confuse:

Partner referral relationship

with:

Partner NFC Card Activation permission.

A Partner can refer schools without having NFC activation permission.

The Platform Owner must explicitly enable NFC Card Activation.

ISSUE 2 — Partner dashboard initially displays 404

When an authorized Partner logs in, the dashboard initially displays:

404 Page Not Found

However, when the Partner clicks/navigates anywhere on the dashboard, the dashboard content then appears and works normally.

This indicates that the Partner dashboard is likely being rendered or routed before the authenticated Partner role/context/navigation state has finished resolving.

Diagnose the actual root cause

Do not simply hide the 404 page.

Trace the initial navigation after successful Partner authentication and determine:

- exact URL/path immediately after login
- route registered for that path
- authentication/session state at first render
- Partner role/context loading
- Partner profile loading
- referral/school scope loading
- permission loading
- route guards
- redirect logic
- lazy-loaded route/module behavior
- whether the first request returns 404
- whether the frontend incorrectly renders a global 404 before authorized context is ready
- whether clicking another dashboard item triggers a second navigation that initializes the missing context

Capture the actual request/response/error responsible for the initial 404.

Fix the root cause rather than masking the 404.

Expected behavior

After Partner login:

1. Authentication completes.
2. Authoritative Partner identity/context is loaded.
3. Partner permissions are loaded.
4. Partner profile/referral scope is loaded.
5. The Partner dashboard route is resolved.
6. The correct Partner dashboard renders immediately.

There must be no intermediate 404 page during normal authenticated Partner login.

A page may show a proper loading state while the authenticated Partner context is being resolved, but it must not show the global "404 Page Not Found" simply because the role/context has not loaded yet.

Refreshing the Partner dashboard directly must also work.

Opening the Partner dashboard URL directly in a new browser tab must also work.

Partner NFC Activation visibility

Once the Platform Owner grants NFC Card Activation permission:

The Partner dashboard/navigation should show:

NFC Activation

or an equivalent clearly named existing navigation item.

If the permission is disabled/revoked:

- NFC Activation must not be available for new activation actions.
- Existing valid card assignments must remain intact.
- Backend authorization must still deny activation even if the Partner manually enters the route.

Partner school scope

The Partner's NFC Activation area must show only:

1. Schools referred by that Partner.
2. Schools with at least one active NFC device linked by the Platform Owner.
3. Schools for which the Partner has NFC Card Activation permission.

Do not expose unrelated schools.

If a referred school has no active NFC device, it may appear in the Partner's school list with:

NFC Activation unavailable — no active NFC device linked.

But the Partner must not be able to assign a card to that school.

NFC device rule

Preserve the existing device-first rule:

Platform Owner links NFC device to school
→ School becomes NFC-enabled
→ Platform Owner grants Partner NFC Card Activation
→ Partner can assign cards to eligible students in that referred school

Partner cannot:

- link a device
- unlink a device
- create a device
- change device-school relationships
- bypass the active-device requirement.

Card assignment

Once authorized, Partner should use the existing NFC card assignment workflow.

The relationship remains:

NFC Card → Student → School

Do not require the Partner to select an NFC device.

If a school has multiple active devices, one valid card assignment automatically works on all active devices belonging to that school.

Security

Backend authorization must independently verify:

- authenticated Partner
- Partner permission
- Partner's referred-school relationship
- school status
- active NFC device
- student belongs to the selected school
- NFC card is valid/available

Do not rely on frontend route visibility.

Test manipulated:

- partner IDs
- school IDs
- student IDs
- card IDs
- device IDs

A Partner must not be able to activate a card for another Partner's school.

Existing internal NFC Activation Officers

Do not change or break the existing Platform Owner employee NFC Activation Officer/Device Activation Officer workflow.

Both internal employees and Partners should ultimately use the existing secure NFC card assignment service.
