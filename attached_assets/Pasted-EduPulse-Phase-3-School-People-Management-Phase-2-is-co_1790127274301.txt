EduPulse Phase 3 — School & People Management

Phase 2 is complete and verified. Continue from the existing EduPulse codebase.

IMPORTANT

DO NOT:

- restart the project
- delete the existing database
- reset existing data
- replace the current architecture unnecessarily
- recreate modules that already work
- remove existing seed records
- break Clerk authentication
- weaken the RBAC or tenant-isolation implemented in Phase 2
- implement the Partner/Reseller system yet

Before changing anything, inspect the current implementation and database schema and reuse existing structures wherever possible.

The goal of this phase is to build a complete, secure School & People Management foundation on top of the Phase 2 authentication/RBAC architecture.

---

1. SCHOOL MANAGEMENT

Improve the existing school management module.

Platform Owner should be able to:

- Create school
- View schools
- Search schools
- Filter schools
- View school details
- Edit school information
- Activate/deactivate a school
- View school status
- View school administrator(s)
- View school statistics
- View subscription status
- View academic setup status

School information should support:

- School name
- School code
- Registration number where applicable
- Address
- State
- LGA
- Phone
- Email
- Website
- Logo
- School type
- School status
- Date created
- Other appropriate institutional information

School codes must remain unique.

School Admin should only see and manage their authorized school(s).

Do not allow users to access another school's data by changing a school ID in the URL, query string, request body, or API call.

Continue deriving authorization from the authenticated user's membership.

---

2. STUDENT MANAGEMENT

Build out the student module into a production-ready foundation.

Student profile should support:

- Student ID
- Admission number
- First name
- Middle name
- Last name
- Date of birth
- Gender
- Passport/photo
- Admission date
- Admission status
- Student status
- Current school
- Current class
- Current section
- Previous school where applicable
- Address
- Medical/emergency information where appropriate
- Parent/guardian relationships
- NFC card association where applicable
- Created date
- Updated date

Support student statuses such as:

- ACTIVE
- INACTIVE
- GRADUATED
- TRANSFERRED
- WITHDRAWN

Do not delete students merely because they leave a school.

Use historical status where appropriate.

Admission number must remain unique within a school.

---

3. STUDENT CLASS ASSIGNMENT

Students must be assignable to:

- Academic session
- Term where appropriate
- Class
- Section

Do not simply overwrite historical class information.

Design the data model so that the system can preserve historical class assignments.

For example:

Student A:

- 2025/2026 → JSS1 → A
- 2026/2027 → JSS2 → B

Historical records must remain available.

A student's current class should be clearly identifiable.

Prevent invalid cross-school class assignments.

15. DATA INTEGRITY

Use database constraints where appropriate.

Examples:

- unique school code
- unique admission number per school
- unique employee ID per school
- unique subject code per school where applicable
- valid school/class relationships
- valid school/student relationships
- valid teacher/class relationships
- valid parent/student relationships
- no duplicate active assignment where prohibited

Use foreign keys and indexes appropriately.

Use additive database migrations.

Do not reset the database.

---

16. API SECURITY

Every new endpoint must use the Phase 2 authorization architecture.

Verify:

- unauthenticated → 401
- authenticated but unauthorized → 403
- resource outside authorized tenant → appropriate scoped response
- inactive user → denied
- school membership required where applicable
- platform-only operations protected

Never trust:

- schoolId from client
- userId from client
- role from client
- parentId from client
- teacherId from client

Validate that the authenticated user actually has access to the requested resource.

21. TESTING

Add automated tests for at least:

Authentication

- unauthenticated request → 401
- inactive user → denied

Tenant isolation

- School A cannot access School B students
- School A cannot access School B parents
- School A cannot access School B teachers
- School A cannot access School B classes
- School A cannot access School B subjects

RBAC

- School Admin cannot create PLATFORM_OWNER
- Teacher cannot manage school users
- Parent cannot modify student records
- Student cannot access another student
- Staff cannot access unauthorized administrative endpoints

Data integrity

- duplicate admission number rejected
- duplicate employee ID rejected
- invalid school/class relationship rejected
- invalid teacher/class relationship rejected
- duplicate parent/student relationship rejected

Historical records

- deactivated parent relationship remains historically available
- previous class assignment remains historically available
- previous teacher assignment remains historically available
- inactive students are not deleted

Audit

- administrative changes create audit records
- authenticated actor is recorded
- unauthorized attempts generate appropriate security events where applicable
