Yemait EduCore — Unified Invitation System Fix

Work ONLY in the development environment.

DO NOT publish, deploy, modify production, run production migrations, modify production data, or change production Clerk configuration.

This task combines two related issues:

1. Invitation links currently fail for some recipients:
   - School Administrator invitation opens a blank page.
   - Company Employee invitation opens a blank page.
   - Partner invitation opens a "Page Not Found" page.
2. Platform Owner needs proper invitation management:
   - Edit incorrect email addresses.
   - Resend invitations.
   - See whether an invitation is still pending or the account is actually active.
   - "ACTIVE" must only appear after the recipient has completed registration and the application has successfully activated their account.

Do not create separate incompatible invitation systems. Fix the existing architecture and make one reliable invitation lifecycle for all applicable roles.

Before changing code, inspect the current implementation of:

- Clerk authentication

- Whether route guards are causing the blank page.

Identify the actual root causes before implementing the fix.

2. CREATE ONE CANONICAL INVITATION ACCEPTANCE FLOW

Use one canonical application route, preferably:

"/accept-invitation"

or preserve an existing equivalent route if one already exists.

The route must work for:

- School Administrator
- Additional School Administrator
- Partner
- Company Accountant
- Device Activation Officer
- Student
- Parent

The acceptance page must:

- Work without an existing application session.
- Wait for Clerk to initialize.
- Never render a blank white screen.
- Display a loading state while authentication is initializing.
- Detect and preserve the invitation context.
- Allow the recipient to complete registration/account setup.
- Securely resolve the invitation through the backend.
- Link the resulting Clerk identity to the correct application record.
- Activate the correct role only after successful registration and backend verification.
- Redirect to the correct role-specific dashboard.

3. FIX THE BLANK PAGE

The School Administrator and Company Employee invitation links currently open the website but display a blank page.

Audit all route guards and authentication conditions.

No route should silently return "null" while:

- Clerk is loading.
- The invitation is being resolved.
- The session is being created.
- The backend is resolving the invitation.
- A redirect is pending.

Instead display appropriate states:

Loading

"Preparing your invitation..."

Invalid

"This invitation is invalid or no longer available."

Expired

"This invitation has expired. Please contact the Platform Owner for a new invitation."

Already accepted

"This invitation has already been accepted. Please sign in."

Registration error

"We could not complete your registration. Please try again or contact the Platform Owner."

Never leave the user with a blank screen.

"Partner Dashboard"

7. CORRECT DEFINITION OF ACTIVE

This is critical.

Do NOT mark an account "ACTIVE" when:

- the record is created;
- an invitation is generated;
- the invitation is sent;
- Clerk accepts the invitation request;
- the email is delivered;
- the recipient opens the invitation;
- the recipient reaches the registration page.

The account must remain pending until registration is actually completed.

The intended lifecycle is:

"Created"

↓

"INVITED / PENDING"

↓

"Invitation opened"

↓

"ACCEPTANCE_IN_PROGRESS"

↓

"Registration completed"

↓

"Backend verifies invitation + Clerk identity"

↓

"Application account linked"

↓

"Role activated"

↓

"ACTIVE"

Only the backend should make the final transition to "ACTIVE".

The frontend must never be able to simply set an account to ACTIVE.

8. OWNER DASHBOARD STATUS

Remove the current UI behavior where an invitation appears as active simply because the invitation exists.

Do not create a misleading separate "Active" section for people who have merely been invited.

For each person, show their actual account/invitation state.

Example:

Person| Email| Status| Actions
John Doe| john@example.com| Pending| Edit Email / Resend
Jane Doe| jane@example.com| Active| Manage

Use appropriate statuses supported by the existing architecture, such as:

- "PENDING"
- "ACCEPTANCE_IN_PROGRESS"
- "ACTIVE"
- "EXPIRED"
- "REVOKED"

Do not add unnecessary database complexity if the existing invitation model can represent these states correctly.

The essential distinction is:

Invitation not completed = NOT ACTIVE

Registration completed and backend account activated = ACTIVE

---

9. PLATFORM OWNER — EDIT EMAIL

The Platform Owner must be able to correct an incorrect email address for a pending:

- School Administrator
- Partner
- Company Employee

Example:

Current:

"wrong@email.com"

Owner changes it to:

"correct@email.com"

The system must:

1. Validate the new email.
2. Update the pending invitation's email.
3. Invalidate/supersede the old pending invitation where necessary.
4. Generate/use a new valid invitation.
5. Send the new invitation to the corrected email.
6. Preserve the intended role.
7. Preserve the correct school/partner/company association.
8. Prevent the old invitation from activating the account incorrectly.
9. Record the email change in the audit log.

Do NOT silently change an already-active user's login email using the pending-invitation workflow.

If an account is already ACTIVE, leave the existing account-email-change process intact.

---

10. PLATFORM OWNER — RESEND INVITATION

For a pending invitation provide:

Resend Invitation

When selected:

- Create/use a valid current invitation.
- Send the invitation again.
- Preserve role.
- Preserve school/partner/company association.
- Do not create duplicate application users.
- Do not create duplicate active roles.
- Record the resend in the audit log.

If the previous invitation has expired or is no longer valid, create a replacement invitation.

The Owner should receive a clear success/error message.

---

11. INVITATION SECURITY

When an email is changed:

- The old pending invitation must be invalidated/superseded.
- The old link must not activate the account using the old email.

When an invitation is resent:

- Stale/superseded links must not create duplicate accounts.
- The newest valid invitation should be authoritative.

Never log:

- invitation tokens
- passwords
- authentication secrets

Audit records should contain appropriate metadata such as:

- invitation created
- original email
- current email
- email changed by
- email-change timestamp
- invitation resent
- resend timestamp
- invitation accepted
- registration completed
- activation timestamp
- intended role
- school/partner/company association
