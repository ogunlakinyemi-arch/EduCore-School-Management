Do NOT blindly replay historical migrations.

The migration groups should generally follow this order, but the exact grouping must be determined from actual dependencies:

Migration Group A — Foundation / missing base structures

Create missing base tables, columns, sequences, primary keys and prerequisite unique structures that do not depend on later application objects.

Requirements:

- preserve existing objects
- do not drop existing production objects
- do not rename existing production objects merely for cosmetic consistency
- do not overwrite existing data
- do not fabricate data
- do not create duplicate equivalent indexes

5. OBJECT-BY-OBJECT RECONCILIATION RULE

For every canonical object, classify it as exactly one of:

1. PRESENT AND EQUIVALENT
2. PRESENT WITH PROVEN EQUIVALENT DIFFERENCE
3. MISSING — SAFE TO CREATE
4. PRESENT BUT DIFFERENT — REQUIRES CONTROLLED RECONCILIATION
5. AMBIGUOUS — STOP

Never use name-only matching.

For constraints and indexes compare:

- columns
- order
- uniqueness
- predicate
- expression
- referenced table
- referenced columns
- ON DELETE
- ON UPDATE
- MATCH behavior
- validation status where applicable
- immediate/deferred behavior where applicable

For functions compare the actual body/definition.

For triggers compare:

- timing
- event
- level
- function
- enabled state
- semantic behavior

---

6. EXISTING OBJECT SAFETY

Every migration must be safe against an already-partially-reconciled database.

Use guarded/idempotent DDL where appropriate.

However:

DO NOT use "IF NOT EXISTS" as a substitute for equivalence checking.

For example, if an index exists with the same name but different definition:

STOP.

Do not silently accept it.

If an existing object is equivalent but differently named:

- preserve it when safe
- record the equivalence
- only create a new named object when required by a dependent canonical constraint or FK
- never drop an existing object merely to normalize naming

---

7. FOREIGN KEY ORDERING

Foreign keys must only be created after:

1. referenced table exists
2. referenced columns exist
3. qualifying unique/primary key exists
4. referenced key has the required uniqueness semantics
5. child columns exist
6. child data safety has been established where the migration will eventually be run against Production

For this BUILD stage, do not connect to Production to perform data checks.

Where Production data validation will be required before applying a migration, mark the migration as having a preflight gate.

Do not fabricate a successful preflight.

---

8. DATA SAFETY

All migrations must be additive/non-destructive.

Forbidden:

- DROP TABLE
- DROP COLUMN
- DROP SEQUENCE
- DELETE
- TRUNCATE
- mass UPDATE
- destructive index replacement
- destructive constraint replacement without an explicit proven-safe plan
- data backfills invented without evidence

A controlled replacement is allowed only where:

- equivalence has been established,
- the dependency graph permits it,
- no data is destroyed,
- the replacement is atomic,
- and it is explicitly documented.

If a required canonical object cannot safely be created without a destructive operation:

STOP and report it.

Do not work around the problem.

10. SPECIAL TENANT-OWNERSHIP RULE

The canonical system is multi-tenant.

Where a relationship is tenant-owned, prefer the canonical composite ownership relationship.

Examples include:

"(student_id, school_id)"

"(academic_session_id, school_id)"

"(academic_term_id, school_id)"

"(subscription_id, school_id, student_id)"

Do not weaken composite ownership relationships into standalone IDs.

Do not add new standalone FKs unless they are explicitly present in the canonical schema.

This is especially important for:

- students
- subscriptions
- academic sessions
- academic terms
- Partner attribution
- Finance allocations
- Finance payments
- device/class ownership

11. PRESERVE THE TRANSFER DECISION

Do not implement student transfer behavior in this stage.

The canonical business rule is:

A student record referenced by historical Finance retains its original school ownership.

A later transfer establishes a separately authorized destination enrollment/ownership identity.

Historical payment, subscription, allocation, Partner attribution, commission and receipt history must remain associated with the original school/accounting period.

The migration must not rewrite historical Finance ownership.
