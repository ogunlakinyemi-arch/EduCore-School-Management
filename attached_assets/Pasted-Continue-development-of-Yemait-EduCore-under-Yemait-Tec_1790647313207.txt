Use the existing intended statuses:

- PENDING
- PROCESSING
- VERIFIED
- FAILED
- REJECTED
- CANCELLED
- REVERSED
- REFUNDED

TASK 4 — PARTIAL PAYMENTS

The backend must:

- calculate outstanding balance

- reject payment amounts greater than permitted balance
- prevent duplicate settlement
- correctly update invoice balance
- correctly update student/parent dashboard
- correctly generate receipts
- handle multiple verified payments against one invoice

TASK 5 — MANUAL BANK TRANSFER

Verify this workflow:

Parent:

1. Selects child.
2. Views invoice.
3. Selects bank transfer.
4. Sees the correct payment instructions.
5. Submits transfer reference/evidence where applicable.

The system must NOT immediately mark the invoice paid.

Authorized school personnel must verify the transfer.

Only after successful verification:

- payment becomes VERIFIED
- invoice balance updates
- receipt becomes available
- notification is generated
- audit entry is created

Rejecting a transfer must not modify the invoice as paid.

TASK 6 — ONLINE PROVIDER PAYMENT

Verify:

Parent:

1. Selects child.
2. Views invoice.
3. Selects an available payment provider.
4. Enters an allowed amount.
5. Backend initializes payment.
6. Parent is redirected/served provider checkout.
7. Provider processes payment.
8. Backend independently verifies the transaction.
9. Backend settles payment only after successful verification.
10. Invoice balance updates.
11. Receipt becomes available.
12. Parent/student dashboard reflects the new balance.
13. Notification is generated.

Do not trust:

- browser redirect
- frontend callback
- client-side success message
- URL parameters
- manually supplied payment status

as proof of payment.
