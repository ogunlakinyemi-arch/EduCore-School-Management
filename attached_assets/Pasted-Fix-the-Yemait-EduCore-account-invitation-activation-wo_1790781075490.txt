- partner commissions;
- partner payouts;

- company financial reports;
- relevant company transaction/receipt records.

- Platform Owner dashboard;
- school administration;
- student administration;
- parent management;
- teacher management;
- attendance;
- academic results;
- school finance;
- NFC/device activation;
- unrestricted school data.

B. DEVICE_ACTIVATION_OFFICER

This is the internal Yemait Technologies employee responsible for NFC/card/device activation.

The officer can access only the restricted activation functionality already implemented in Task #24.

Do not make either employee a School Staff membership merely because they interact with schools.

2. PLATFORM OWNER NFC ACCESS

Platform Owner must also have access to the SAME NFC card activation workflow as the Device Activation Officer.

The Platform Owner should be able to:

School
→ select linked NFC device
→ Hardware UID automatically populated/read-only
→ select student
→ enter/scan NFC card number
→ assign card
→ view updated e-ID
→ generate/send for printing.

The Platform Owner must NOT need to create or impersonate a Device Activation Officer to perform this operation.

However, this does NOT mean that Device Activation Officer permissions should be added to every Platform Owner permission.

Instead:

- Platform Owner retains existing Platform Owner permissions.
- Platform Owner is additionally authorized to use the NFC activation workflow.
- Device Activation Officer remains restricted to NFC/device activation.
- Both roles use the same backend activation service and security checks.
- Do not duplicate the NFC activation implementation.

The existing server-side validation must apply to both roles.

3. NFC ACTIVATION WORKFLOW

Preserve the Task #24 workflow:

School
→ NFC Device
→ Student
→ NFC Card
→ Assign
→ Updated E-ID
→ Print.

Hardware UID

The Hardware UID/device serial must automatically come from an NFC device already linked to the selected school.

It must be:

- automatically populated;
- read-only;
- never manually typed.

If multiple active NFC devices belong to the school, allow the authorized user to select the device.

The backend must independently verify:

- device belongs to selected school;
- user has authorization to use the device.

Student

Use a searchable Student dropdown.

Only students belonging to the selected school may appear.

Do not require manual Student ID entry.

NFC Card Number

The officer/Owner enters or scans the physical NFC card number.

Keep:

Hardware UID = physical NFC device identifier

NFC Card Number = physical student card identifier

Prevent duplicate active card assignments.

Do not silently reassign an active card.

Preserve existing card replacement/deactivation and activation history where available.

4. PERMANENT STUDENT E-ID CARD DESIGN

IMPORTANT CORRECTION:

The permanent student NFC/e-ID card must NOT contain Class or Section.

Students use the same physical card throughout their time at the school, potentially from admission until graduation.

Therefore, do NOT print/change these academic fields on the permanent physical card:

- Class
- Section
- Current academic session
- Current term

The card should contain stable student identity information instead.

The permanent e-ID should include, where supported:

- School logo
- Student passport/photo
- Student full name
- Student ID
- NFC card number/reference
- School identity information
- Any other permanent/stable identifier already supported
- QR/reference information if already supported

Do not put temporary academic information such as current class or section on the permanent physical card.

The student's current class/section should remain available inside the digital Student Profile and other authorized dashboards.

If the existing e-ID template currently prints Class/Section, remove those fields from the permanent card template.

Do NOT create a separate physical card every time the student changes class.
