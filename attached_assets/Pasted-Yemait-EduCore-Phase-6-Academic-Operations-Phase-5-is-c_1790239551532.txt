PHASE 6 — ACADEMIC OPERATIONS

Build the Academic Operations layer for Yemait EduCore.

Phase 6 must cover:

1. Assignments
2. Examinations/Assessments
3. Results
4. Report Cards
5. Timetable

These modules must integrate with the existing:

- Schools
- Academic sessions
- Terms
- Classes
- Sections
- Students
- Teachers
- Subjects
- Class-subject mappings
- Teacher/class/subject assignments
- Historical student class assignments
- RBAC
- Tenant isolation
- Audit logging

Reuse existing entities wherever possible. Do not create duplicate school, student, teacher, class, section, subject, session, or term systems.

==================================================

1. ASSIGNMENTS
   ==================================================

Implement a complete assignment workflow.

Teachers can create assignments only for:

- their school
- classes they teach
- subjects they are assigned to
- authorized academic session/term

Assignment fields should include:

- title
- description/instructions
- school
- academic session
- term
- class
- section where applicable
- subject
- teacher
- issue date
- due date
- maximum score
- status

Suggested statuses:

DRAFT
PUBLISHED
CLOSED
ARCHIVED

Students can view only assignments applicable to themselves.

Parents can view assignments only for their linked children.

Parents must not access unrelated students or other schools.

Do not build an unnecessary complex file-upload system unless existing infrastructure already supports it.

==================================================

3. RESULT ENTRY

Implement secure result entry.

Teachers may enter results only for:

- subjects they teach
- classes they are assigned to
- students in the relevant academic class/section
- their authorized school
- the correct academic session and term

Result fields should include:

- student
- subject
- assessment
- score
- maximum score
- grade where applicable
- grade point where applicable
- remark where applicable
- teacher
- academic session
- term
- historical class/section context
- timestamps

Validation:

- score cannot be negative
- score cannot exceed maximum score
- student must belong to the academic context
- assessment must belong to the same school
- subject must belong to the correct school
- teacher must be authorized
- prevent accidental duplicate result records

Do not silently create duplicates.

==================================================
4. RESULT APPROVAL AND PUBLICATION

Separate result entry from result publication.

Teachers may enter/edit results while permitted.

School Admin can review and publish results.

After publication:

- Student can view own result
- Parent can view linked child's result
- Unauthorized users cannot view results
- Students and parents cannot modify results

Changes to published results require appropriate authorization and must generate audit records.

==================================================
5. GRADING SYSTEM

Implement configurable grading.

The system should support school-specific grading rules containing:

- minimum score
- maximum score
- grade
- grade point where applicable
- remark

A grading configuration must not silently rewrite historical published results.

Automatic grade calculation, if implemented, must be deterministic and tested.

6. REPORT CARDS

Implement report-card generation/viewing.

Each report card must be tied to:

- student
- school
- academic session
- term
- class
- section where applicable

Display appropriate information such as:

- student name/identity
- class
- section
- subjects
- assessment scores
- totals
- averages
- grades
- grade points where configured
- teacher remarks
- school/admin remarks where configured
- attendance summary where appropriate
- promotion/status information where configured

Do not fabricate missing academic data.

If results are missing or unpublished, clearly indicate that state.

Parents can only view report cards for linked children.

Students can only view their own report cards.

==================================================
7. HISTORICAL REPORT CARD INTEGRITY

Historical academic records must remain tied to their original academic context.

Example:

2026/2027 Term 1 → JSS2 Emerald

Later:

2027/2028 Term 1 → JSS3 Ruby

The old report card must continue showing JSS2 Emerald.

A future class change, section change, teacher reassignment, subject reassignment, or grading configuration change must not rewrite historical published records.

Use historical references/snapshots where necessary.

==================================================
8. TIMETABLE

Implement timetable management.

Each timetable entry should support:

- school
- academic session
- term where appropriate
- class
- section
- subject
- teacher
- day
- start time
- end time
- room/location where applicable

Support normal school days while allowing future configurability.

Prevent conflicts.

At minimum detect:

TEACHER CONFLICT:
A teacher cannot teach two classes at the same time.

CLASS CONFLICT:
A class/section cannot have two subjects at the same time.

ROOM CONFLICT:
If rooms are implemented, a room cannot be used by two simultaneous entries.

Return a validation error instead of silently overwriting entries.
