EduPulse Phase 5 — Attendance, NFC Identification & Biometric Architecture

Phase 4 has been completed, merged, and verified.

Continue from the existing EduPulse codebase.

CRITICAL RULES

DO NOT:

- restart the project
- rebuild the application from scratch
- reset the database
- delete existing data
- remove existing modules
- weaken Clerk authentication
- weaken RBAC
- weaken tenant isolation
- break Partner/Reseller functionality
- modify historical subscription records
- remove existing partner commission records
- implement unrelated modules

First inspect the current Phase 1–4 architecture and reuse the existing systems.

Use additive database migrations.

The system must remain multi-tenant and school-scoped.

---

1. OBJECTIVE

Build the foundation for EduPulse attendance and student identification.

The system must support:

1. School entry attendance
2. School exit attendance
3. Classroom attendance
4. NFC student identification
5. Biometric/fingerprint identification architecture
6. Staff attendance foundation
7. Attendance reconciliation
8. Parent notifications foundation
9. Device registration and school assignment
10. Device security and school binding
11. Attendance history
12. Attendance reporting

The system must distinguish:

Student is physically present at school

from:

Student is present in their assigned classroom

These are NOT the same event.

---

2. ATTENDANCE MODEL

Create separate attendance events.

SCHOOL ENTRY

When a student enters the school:

Student → School Entry Device → Attendance Event

Record:

- Student
- School
- Date
- Time
- Device
- Identification method
- Event type
- Result
- Session/term
- Created timestamp

Event type:

"SCHOOL_ENTRY"

---

3. SCHOOL EXIT

When a student leaves:

Event type:

"SCHOOL_EXIT"

Record:

- Student
- School
- Date
- Time
- Device
- Identification method
- Result
- Session/term

---

4. CLASSROOM ATTENDANCE

Classroom attendance must be independent of school entry.

Event type:

"CLASSROOM_ENTRY"

or an equivalent attendance representation appropriate to the architecture.

The system should determine:

- Student's current class
- Student's current section
- Expected classroom
- Actual classroom/device
- Date
- Time
- Identification method

This prevents the following problem:

Student enters school at 7:30 AM.

But never enters their classroom.

The system must be capable of identifying:

School present = YES

Class present = NO

5. ATTENDANCE STATUS

Create meaningful attendance states.

Examples:

- PRESENT
- ABSENT
- LATE
- LEFT_EARLY
- EXCUSED
- UNKNOWN
- MISMATCH

Do not hard-code attendance percentages.

6. NFC STUDENT IDENTIFICATION

Use the existing NFC card foundation.

Inspect the current:

- NFC card table
- NFC status management
- student relationship
- subscription eligibility
- school ownership checks

Extend it safely.

Each NFC card should have:

- NFC UID
- Student ID
- School ID
- Card status
- Activation date
- Expiry/renewal information where applicable
- Issued date
- Last used timestamp
- Device/reader information where appropriate

Possible card states:

- ACTIVE
- INACTIVE
- LOST
- BLOCKED
- REPLACED
- EXPIRED

Do not allow the same active NFC UID to belong to multiple students.

Do not allow a card belonging to School A to authenticate a student at School B.

- Activate card
- Deactivate card

- View card history

The old card must remain historically recorded.

Do not delete historical NFC records.

---

9. DEVICE SCHOOL BINDING

This is a critical security requirement.

Once a device is configured for School A:

It must NOT be able to submit attendance events for School B.

The device must be associated with a specific school.

Attendance requests must validate:

Device → School → Student → Attendance event

All four relationships must be valid.

Do not trust school ID supplied by the device alone.

Use secure device authentication/credentials.

---

10. DEVICE REGISTRATION

Platform Owner should be able to:

- Register device
- Assign device to school
- Activate device
- Suspend device
- Unassign device
- View device status
- View device location
- View last activity

School Admin may view authorized devices according to permissions but should not be able to reassign devices across schools unless explicitly authorized.

---

11. DEVICE CONFIGURATION

Design a configuration system that allows the company to configure a device for a school.

Example:

Device:
"EDU-NFC-001"

Assigned school:
"School A"

Location:
"Main Gate"

Device type:
"NFC_READER"

Once assigned:

Device can only process authorized attendance events for School A.

If reassignment is required:

Require an explicit authorized reassignment workflow.

Record the reassignment in audit history.

---

12. DEVICE SECURITY

Implement device authentication.

Do NOT rely only on:

- device ID
- school ID
- serial number

Use a secure credential/token/key mechanism appropriate to the architecture.

Credentials should be:

- unique
- revocable
- rotatable
- securely stored
- redacted from logs

Do not store raw device secrets in ordinary audit records.

---

13. BIOMETRIC/FINGERPRINT ARCHITECTURE

Do NOT attempt to build a fake fingerprint scanner using the browser.

Create an integration-ready biometric architecture.

The application should support future external biometric hardware.

Define an abstraction such as:

"BiometricProvider"

or equivalent architecture.

The application should be able to receive:

- device identifier
- school identifier
- biometric match result
- student identifier where securely resolved
- timestamp
- confidence/result metadata where provided by hardware

The actual fingerprint matching may be performed:

- on the biometric device
- through the manufacturer's SDK
- through a local school gateway
- through a secure biometric service

Do not assume browser fingerprint access.

---

14. BIOMETRIC PRIVACY

Do NOT store raw fingerprint images/templates unless absolutely required and legally/technically justified.

Prefer storing:

- biometric enrollment reference
- provider reference
- device reference
- status
- enrollment timestamp

If biometric templates are ever stored, they must use a dedicated secure architecture.

Do not expose biometric data through normal parent/student APIs.

---

15. YOUNGER CHILDREN

The architecture must support students who may not be suitable for fingerprint enrollment.

A student can have an identification policy such as:

- NFC_ONLY
- BIOMETRIC_ONLY
- NFC_AND_BIOMETRIC
- MANUAL_FALLBACK

Do not force fingerprint enrollment for every student.

The school should be able to configure the identification method according to age and school policy.

17. ATTENDANCE EVENT PROCESSING

Attendance events must pass validation:

1. Device exists
2. Device is active
3. Device belongs to the correct school
4. Identification is valid
5. Student exists
6. Student belongs to the school
7. Student is active/eligible where appropriate
8. Event type is valid
9. Timestamp is valid
10. Duplicate event rules are satisfied

Only then create the attendance event.

---

18. DUPLICATE ATTENDANCE

Prevent accidental duplicate events.

For example:

Student taps NFC five times within a few seconds.

Do not create five separate attendance records unless the event semantics require it.

Implement a configurable duplicate suppression window.

Example:

Same student
Same device
Same event type
Within 30 seconds

→ treat as duplicate/repeat event.

Do not hard-code 30 seconds throughout the system.

Make the setting configurable.

---

19. SCHOOL PRESENCE RECONCILIATION

Create a reconciliation engine.

Example:

Student enters school:

"SCHOOL_ENTRY = PRESENT"

But no classroom attendance is recorded within the expected classroom window.

System should identify:

"CLASSROOM_ATTENDANCE = MISSING"

Potential status:

"MISMATCH"

The system must distinguish between:

- school present/class absent
- school absent/class present
- school present/class present
- school exit without entry
- duplicate entry
- invalid device event

Do not automatically accuse a student of wrongdoing.

The system should identify the attendance discrepancy for authorized school staff.

---

20. CLASSROOM ASSIGNMENT

Use the existing Phase 3 class assignment.

Attendance must determine the student's expected class from the current valid assignment.

Do not allow the client to simply claim:

"studentClassId = X"

and bypass the actual student assignment.
