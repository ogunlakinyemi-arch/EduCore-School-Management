YEMAIT EDUCORE — EMAIL + PUSH + SMS NOTIFICATION INTEGRATION

1. DEVELOPMENT-ONLY REQUIREMENT

Work ONLY in the Replit Development environment.

DO NOT click, execute, or initiate Publish.

Do not modify Production database, Production schema, Production data, Production secrets, or deployment configuration.

The existing Replit Publish/schema-diff generator issue is being handled separately through Replit Support. Do not attempt to fix, bypass, or work around it.

Do not delete, reset, or replace existing notification functionality.

---

2. OBJECTIVE

Connect the existing Yemait EduCore notification and Parent Communication Centre to three external delivery channels:

1. Email
2. Web Push / PWA Push Notifications
3. SMS

The existing notification workflows must remain intact.

Do NOT create a second notification system.

Extend the existing notification engine so that one application event can optionally produce:

EduCore Event
      ↓
Existing Notification Engine
      ↓
Channel Selection
 ┌────┼────┐
 ↓    ↓    ↓
Push SMS Email

The existing in-app notification/inbox functionality must continue working exactly as it does now.

---

3. PROVIDER ARCHITECTURE

Implement provider adapters/interfaces rather than hard-coding providers throughout the application.

Use interfaces similar to:

EmailProvider
SmsProvider
PushProvider

The application should depend on these interfaces, not directly on a specific vendor.

Recommended initial providers:

Email

Use Resend as the initial email adapter.

SMS

Use Termii as the initial SMS adapter.

Push

Use standard Web Push / VAPID for the PWA rather than requiring a separate push vendor.

Keep the architecture replaceable so another provider can be added later without changing the notification workflows.

Do not claim that external providers are live or configured unless actual credentials are available.

8. EMAIL IMPLEMENTATION

Create or extend an EmailProvider adapter using Resend.

Requirements:

- Send transactional email only.
- Use verified sender/domain configuration.
- Support HTML and plain-text fallback where practical.
- Do not expose API keys.
- Return structured success/failure results.
- Record delivery attempt status.
- Do not crash the main notification workflow merely because an email provider is unavailable.
- Preserve the in-app notification even if email delivery fails.

Suggested result structure:

success
provider
messageId
errorCode
errorMessage

Never store sensitive provider credentials in the database.

---

9. SMS IMPLEMENTATION

Create or extend an SmsProvider adapter using Termii.

Requirements:

- Nigerian phone-number handling.
- Normalize phone numbers consistently.
- Validate recipient phone numbers before sending.
- Respect notification preferences.
- Support emergency/security SMS where business rules require it.
- Record delivery attempt status.
- Use idempotency protection.
- Do not send duplicate SMS because of repeated event processing.
- Do not expose API credentials.
- Preserve the in-app notification when SMS fails.

Do not send real SMS during automated tests unless an explicit safe test adapter is being used.

---

10. WEB PUSH / PWA IMPLEMENTATION

Use Web Push with VAPID.

Inspect the existing PWA/service-worker implementation before changing anything.

Implement:

Browser
   ↓
Notification permission
   ↓
Push subscription
   ↓
EduCore backend
   ↓
User/device subscription

Store push subscriptions securely and associate them with the authenticated user/device.

Support:

- Multiple devices per user.
- Multiple parent devices.
- Subscription replacement.
- Subscription expiration.
- Invalid subscription cleanup.
- Logout/session considerations.
- Revoked/expired subscriptions.
- Tenant isolation.

Do not store authentication passwords in local storage.

Do not cache sensitive notification data unnecessarily.

---

11. PUSH PAYLOAD SECURITY

Do not place unnecessary sensitive information directly into push payloads.

For sensitive events, prefer a minimal notification such as:

Your child's attendance has been updated.
Open Yemait EduCore for details.

rather than exposing confidential information on a locked phone screen.

Security-sensitive information should require opening the authenticated application where appropriate.

13. IDEMPOTENCY / DUPLICATE PROTECTION

This is mandatory.

A single event must not accidentally send:

- two SMS messages
- two emails
- two push notifications

because of retries, page reloads, queue retries, webhook retries, or repeated event processing.

Use an idempotency key based on the existing event/notification identity and channel.

Conceptually:

event_id + recipient_id + channel

must not result in duplicate delivery attempts for the same notification unless an explicit retry policy allows it.

---

14. FAILURE HANDLING

External delivery failure must not break the core EduCore workflow.

Example:

Student arrives
      ↓
Security event saved successfully
      ↓
Parent notification created
      ↓
Push attempt fails
      ↓
Notification remains in EduCore
      ↓
Failure recorded

Do not roll back the underlying school event merely because SMS/email/push delivery failed.

Support safe retry where appropriate.

≠
