3. CLERK AUTHENTICATION

Integrate Clerk into the existing application.

Use Clerk for:

- Sign up
- Sign in
- Sign out
- Session management
- Current authenticated identity

Do not store Clerk passwords.

Use environment variables for Clerk configuration.

The backend must validate authenticated requests using Clerk.

The frontend must use Clerk authentication state for protected application routes.

4. INTERNAL EDUPULSE USER

Create an internal application user model that maps Clerk users to EduPulse users.

Recommended structure:

app_users

Fields should include appropriate equivalents of:

- id
- clerk_user_id
- email
- first_name
- last_name
- phone
- status
- created_at
- updated_at

Requirements:

- clerk_user_id must be unique.
- Internal user ID must be used by the application's relational database.
- Do not use email as the permanent identity key.
- User records must have an active/inactive status.

If the existing architecture has an equivalent table, extend it rather than creating another identity table.

---

5. USER PROVISIONING

When an authenticated Clerk user first accesses EduPulse:

Determine whether an internal EduPulse user exists.

If not, create/provision the appropriate internal user record according to the application's approved onboarding flow.

Do not automatically grant privileged roles.

New users must never automatically become:

- PLATFORM_OWNER
- SCHOOL_ADMIN

unless an authorized provisioning process explicitly assigns the role.

7. SCHOOL MEMBERSHIP

Create a school membership/role-assignment architecture.

A user may have:

school_memberships

- id

- Indexes
- Unique constraints

Prevent duplicate active membership assignments.

---

8. ROLE ASSIGNMENT SECURITY

Only authorized administrators may assign school roles.

Rules:

PLATFORM_OWNER:

- Can manage authorized platform users and school memberships.

SCHOOL_ADMIN:

- Can manage users within their own school only.
- Cannot create or assign PLATFORM_OWNER.

TEACHER:

- Cannot change roles.

ACCOUNTANT:

- Cannot change roles unless explicitly authorized.

PARENT:

- Cannot change roles.

STUDENT:

- Cannot change roles.

STAFF:

- Cannot change roles.

No user may promote themselves.

No client-supplied role may be trusted without server-side authorization.

---

9. AUTHORIZATION MIDDLEWARE

Create reusable backend authorization functions/middleware.

At minimum support concepts equivalent to:

requireAuthentication()

requireRole()

requirePermission()

requireSchoolMembership()

requireSchoolAccess()

requirePlatformAccess()

Names may follow the existing codebase conventions.

Authorization must happen on the backend.

Frontend route hiding is NOT security.

---

10. AUTHENTICATED SCHOOL CONTEXT

For school-scoped users:

Do not trust:

?schoolId=schoolB

or:

/schools/schoolB/students

simply because the client supplied that ID.

The backend must determine:

- Who is authenticated?
- What role do they have?
- Which school(s) are they authorized to access?
- Is the requested resource inside their authorized scope?

A School Admin from School A must not access School B.

A Teacher from School A must not access School B.

A Parent must not access unrelated school records.

---

11. PLATFORM OWNER ACCESS

PLATFORM_OWNER is the only role that should have platform-wide access at this stage.

Platform Owner may:

- View schools
- View school details
- Manage schools
- View platform subscription information
- View authorized platform audit information
- Manage authorized users

All platform-wide access must still be authenticated.

Do not create an anonymous administrator.

13. STUDENT API SECURITY

Existing endpoints such as:

GET /students?schoolId=...

POST /students?schoolId=...

PATCH /students/:studentId?schoolId=...

must be protected.

For each request:

1. Authenticate user.
2. Determine authorized school context.
3. Verify permission.
4. Verify student belongs to authorized school.
5. Perform operation.

A malicious user must not be able to change schoolId and access another school's students.

---

14. PARENT API SECURITY

Protect parent endpoints similarly.

A School Admin can access parents within their school.

A Parent user must not receive the entire school's parent directory.

A Parent user should only receive information necessary for:

- Their own profile
- Their linked children

---

15. CLASS API SECURITY

Class and section operations must be school-scoped.

A user from School A must not:

- View School B classes
- Create a class in School B
- Modify School B classes
- Delete School B classes

---

16. SUBSCRIPTION API SECURITY

Protect:

- Subscription list
- Subscription creation
- Subscription verification
- Subscription status

A user must not be able to manipulate another school's subscription simply by changing a subscription ID or school ID.

Subscription verification must verify:

- Authenticated user
- Appropriate permission
- Subscription ownership/school
- Valid transaction state

Do not change the existing financial allocation in this phase.

Keep the current:

₦5,000 total

₦2,000 school share

₦3,000 EduPulse share

Partner commission will be integrated later.

---

17. NFC API SECURITY

The audit specifically identified NFC status updates as a security gap.

Harden all NFC operations.

For:

GET NFC cards

Register NFC card

Update NFC card status

Replace NFC card

etc.

Verify that:

- User is authenticated.
- User has appropriate permission.
- Card belongs to the authorized school.
- Student associated with card belongs to authorized school.

A user must not be able to modify an NFC card belonging to another school simply by knowing its card ID.

---

18. SCHOOL API SECURITY

Protect:

GET school

PATCH school

School creation

School management

School Admin may manage their own school.

Platform Owner may manage platform schools.

A School Admin must not modify another school by changing the route ID.

- Primary guardian
- Emergency contact
- Contact priority

- Created date
- Updated date

- Father
- Mother
- Guardian
- Grandparent
- Other

Do not assume one student has only one parent.

23. RELATIONSHIP RULES

Support:

One parent → multiple students.

One student → multiple parents.

Prevent duplicate active parent/student relationships.

Use a database uniqueness constraint where appropriate.

Do not delete historical relationship data unnecessarily.

Use inactive status where historical preservation is required.

parent_phone

Use these values to assist with migration into the normalized relationship table.

7. Do not destroy existing data.
