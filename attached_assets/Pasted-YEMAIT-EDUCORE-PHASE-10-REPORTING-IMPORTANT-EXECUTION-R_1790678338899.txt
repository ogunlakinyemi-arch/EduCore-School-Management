YEMAIT EDUCORE — PHASE 10: REPORTING

IMPORTANT EXECUTION RULE

Implement Phase 10 — Reporting in DEVELOPMENT ONLY.

DO NOT:

- Publish
- Deploy to production
- Modify the production database
- Run production SQL
- Modify production users
- Modify production environment variables/secrets
- Change production authentication configuration
- Replace existing dashboards
- Redesign the Platform Owner dashboard
- Rebuild completed modules unnecessarily
- Change existing Finance, Attendance, Academic, Communication, Library, Operations, Partner or NFC business logic unless a reporting integration requires a minimal read-only adapter

The existing production environment must remain untouched.

This phase is for the development environment and disposable test databases only.

---

1. OBJECTIVE

Build a centralized, secure and role-aware Reporting module for Yemait EduCore.

Reporting must aggregate data from the modules already implemented:

- Schools
- Students
- Parents
- Teachers/staff
- Classes/sections
- Academic sessions/terms
- Subjects
- Teacher assignments
- Attendance
- NFC/device activity
- Academic assessments/results
- Timetable
- Finance
- Subscriptions
- Partners
- Communication
- Library
- Operations
- Audit/history where appropriate

The Reporting module must NOT become a second source of truth.

Reports must read from the existing authoritative domain tables/services.

---

2. REPORTING PRINCIPLE

Reporting is primarily READ-ONLY.

Do not allow reports to directly modify:

- Students
- Parents
- Teachers
- Classes
- Attendance
- Results
- Payments
- Invoices
- Subscriptions
- NFC cards
- NFC devices
- Library loans
- Assets
- Maintenance requests
- Communication records

If a report needs a correction, the correction must happen in the originating module.

---

3. ROLE-BASED REPORT ACCESS

Implement server-side authorization.

PLATFORM OWNER

Platform Owner can access platform-level reports across authorized schools.

Examples:

- Total schools
- Active schools
- Student counts by school
- Student counts by class/session
- Subscription status
- Subscription revenue summaries
- Partner-attributed schools
- Partner commission summaries
- NFC device/card deployment
- Attendance summaries by school
- Academic performance summaries by school
- Communication usage
- Library usage
- Operations summaries
- System activity/audit summaries

Platform Owner must not automatically inherit School Admin write permissions.

Reports must remain read-only.

Owner school selection must remain a platform-level reporting/read-only context.

Do NOT use the reporting module to reintroduce the previously identified Owner-vs-School-Admin UI problem.

15. REPORT EXPORTS

Implement development-ready exports where technically appropriate.

Support:

- CSV
- XLSX
- PDF

Exports must respect exactly the same authorization rules as on-screen reports.

A user must never be able to manipulate a report URL or export request to obtain another school's data.

Every export should use the same server-side query authorization as the corresponding report.

Do not expose hidden columns merely because an export endpoint is called directly.

---

18. SCHOOL REPORTING

School Admin should have a school-specific reporting context.

Every query must enforce:

school_id = authenticated user's authorized school scope

Do not trust:

- URL school_id
- query parameter school_id
- request body school_id
- frontend state

The server must determine the authorized school scope.

---

19. PARENT REPORTING

Parents should only receive reports concerning their linked children.

Potential reports:

- Child attendance
- Child academic results
- Child library activity
- Relevant fee/payment summaries
- Relevant notifications

A parent must never query arbitrary student IDs to obtain another student's reports.

Enforce existing parent-child relationship rules server-side.

---

20. STUDENT REPORTING

Students should only access their own authorized information.

Potential reports:

- Own attendance
- Own results
- Own academic history
- Own library activity
- Own relevant subscription/fee status where existing permissions allow it

No cross-student access.

---

21. TEACHER REPORTING

Teachers should only access reports permitted by their existing school/class/subject permissions.

Examples:

- Assigned class attendance
- Assigned subject performance
- Assessment completion
- Class result summaries
- Relevant academic reports

Do not grant teachers School Admin reporting privileges.

---

22. ACCOUNTANT REPORTING

Accountants should have appropriate school-scoped Finance reports.

Do not expose unrelated Platform Owner or cross-school reports.

Respect existing Finance RBAC.

---

23. AUDITABILITY

Important reporting actions should be auditable where appropriate.

Examples:

- Report generated
- Export generated
- Report type
- User
- School scope
- Timestamp
- Relevant filter context

Do not store sensitive report contents unnecessarily.

Do not log passwords, authentication tokens, cookies or secrets.

---

24. SECURITY REQUIREMENTS

Every Reporting API must have:

- Authentication
- Role authorization
- School tenant isolation
- Object-level authorization
- Parent-child authorization where applicable
- Partner visibility restrictions
- Teacher scope restrictions
- Accountant scope restrictions
- Student self-access restrictions
- Platform Owner authorization

Test direct API access.

Do not rely on frontend hiding alone.

Test:

- Missing authentication → 401
- Unauthorized role → 403
- Wrong school → denied
- Wrong student → denied
- Wrong parent-child relationship → denied
- Unauthorized export → denied

---

25. PERFORMANCE

Reporting queries must be designed for real school usage.

Avoid loading entire tables into the frontend.

Use:

- Server-side aggregation
- Pagination
- Appropriate indexes
- Date-range filtering
- Parameterized queries
- Efficient joins
- Summary queries
- Existing database constraints

Do not introduce premature caching that could cause stale financial or academic information unless explicitly required.

---

26. DATA ACCURACY

Reports must use authoritative existing records.

For example:

Finance reports must derive payment totals from existing Finance payment records.

Attendance reports must derive attendance from existing attendance records.

Academic reports must derive results from existing academic records.

Library reports must derive loans from existing library records.

Do not duplicate records merely to make reporting easier.

If an aggregation cannot be calculated reliably from existing data, document the limitation instead of inventing a value.

---

27. DATABASE

If new reporting tables are genuinely required, minimize them.

Prefer reporting queries/views/services over duplicating domain data.

If migrations are required:

- Create properly numbered migrations after the current development migration state.
- Make them safe and deterministic.
- Test them on a clean disposable PostgreSQL database.
- Test migration replay from the beginning.
- Do not blindly run migrations against the existing development database if the migration ledger is already behind the live schema.
- Do not touch production.

Do NOT create a separate duplicate database for reporting.

- Reports use authoritative existing data.
- All roles are correctly restricted.
- Tenant isolation is enforced server-side.

- Platform Owner reporting remains separate from School Admin operations.
- Finance reporting is read-only.
- Attendance reporting is read-only.
- Academic reporting is read-only.
- Library reporting is read-only.
- Operations reporting is read-only.
- NFC reporting respects school binding.
- Exports respect all permissions.
- Automated tests pass.
- Typechecks pass.
- Builds pass.
- Migration replay passes if migrations were added.
- Production remains untouched.
- Publish is NOT executed.
