# Resend transactional email in Development

## Architecture

Use the existing communication notification and delivery ledgers, replaceable
EmailProvider, ResendEmailProvider, scheduler and campaign/retry dispatcher.
No new database tables or schema changes are required. Queueing happens inside
the existing domain transaction; provider dispatch happens after commit.

Existing, stably keyed parent events add an EMAIL delivery for ATTENDANCE,
ACADEMIC, FINANCE, PAYMENT, ANNOUNCEMENT and SECURITY. Existing ACCOUNT and
SYSTEM notifications also receive an email delivery. Parent selection uses
active profiles, relationships and child-school authorization. Existing
notification preferences and explicit campaign channel choices are preserved.
This adds a channel to existing rules, not new notification triggers.

Clerk remains responsible for authentication invitations, verification and
password-related messages. Do not duplicate Clerk invitations via Resend.
App-generated account/system notifications use the communication ledger.

## Server-side configuration

| Variable | Purpose |
|---|---|
| RESEND_API_KEY | Server-side secret. Never expose to the client, logs or documents. |
| COMMUNICATION_EMAIL_PROVIDER | `resend` selects the existing adapter. |
| EMAIL_FROM | `Yemait EduCore <notifications@yetenia.com>`; configurable. |
| RESEND_DEVELOPMENT_RECIPIENTS | Comma-separated, explicitly approved controlled inboxes. Never add real parents merely to enable testing. |
| NODE_ENV | Managed Development workflow uses `development`. |

Provider and sender settings are scoped to Development. Do not change shared
or Production settings, publish, or move secrets between environments.
Without approved recipients the Development worker explicitly simulates delivery,
with no external email/SMS/push. A directly configured Development Resend provider
rejects recipients outside the allowlist. With an allowlist, email alone can use
the configured provider; SMS/push remain no-network.

## Reliability and evidence

The existing unique event/recipient key and notification/channel uniqueness
deduplicate queueing. Dispatch commits the claim before calling the provider,
rechecks current recipient/school authorization and sends the stable
`communication-{notificationId}-email` Idempotency-Key.
Provider errors are recorded as sanitized categories, not raw responses or keys.
Timeouts, network failures, malformed success responses and 5xx outcomes are
uncertain: hold for reconciliation instead of blindly resending. Confirmed
rejections such as rate limiting retain the existing bounded retry policy.

Resend retains idempotency keys for 24 hours. Local durable state and uncertain
outcome handling must remain in place; do not rely on indefinite provider
deduplication. Provider acceptance is not inbox delivery. Use Resend delivery
evidence and a controlled recipient's inbox confirmation before claiming delivery.

## yetenia.com configuration

Add/verify the intended sending domain in the Resend account. Publish the exact
DKIM and SPF/return-path records generated by that account (TXT/MX or CNAME as
specified), and wait for verification. Do not guess DNS values, overwrite
unrelated mail records or add a second SPF policy at the same name. DMARC is
recommended. The API key must be valid and permitted to send using this domain.

A read-only domain check during implementation returned HTTP 401. The sender
domain could not be verified and no real email was sent. Resolve authentication
through the secure Secrets flow, approve a controlled recipient, then perform
a Development test through the existing delivery service. Do not contact real
parents or change Production to complete that verification.
