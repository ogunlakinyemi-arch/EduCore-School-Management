Development only · Code inspection: 7 October 2026 · Evidence: current workspace implementation and two unauthenticated HTTPS checks.

Scope: This describes the existing integration, updated for the Development idempotency implementation. No application database structure/data, permissions, payments, card assignments, UI, or Production settings were changed during that implementation. Automated tests use private disposable PostgreSQL fixtures. Example identities and credentials are placeholders. Authenticated physical hardware tests were not executed.

1. Purpose

Integrate an external NFC attendance terminal with the existing backend. A suitable student ingestion endpoint and dedicated device credentials already exist. Device identity and school are derived by EduCore, not chosen by firmware.

Important security distinction: the API records attendance and, for school entry/exit NFC events, integrates with campus security identity checks. It does not return a literal ALLOW/DENY property, gate-open command, pickup authorization, or physical actuator instruction. A successful receipt confirms an accepted event; it must not be treated as blanket authority to release a child or open a physical gate.

4. Authentication

A dedicated device authentication credential is implemented. Send the complete issued value in this header on every scan:

X-Device-Credential: <development-credential-identifier>.<development-device-secret>
Content-Type: application/json

The issuing endpoint generates an identifier of the form dev_ plus 24 hexadecimal characters and a 32-byte random secret encoded as base64url. Firmware should treat the complete credential as an opaque secret, not construct it itself. The raw secret is returned at issuance; only its SHA-256 digest is stored by the backend. Validation compares the digest with a timing-safe comparison.

  • Authorization: Bearer ... is not the device authentication mechanism. Human Clerk credentials must not be substituted.
  • The credential must be ACTIVE, unexpired if an expiry is set, and bound to the device's current school.
  • The device must have status ACTIVE, a non-null school, and configuration_status = CONFIGURED. Student NFC ingestion also rechecks NFC/HYBRID device type inside the transaction.
  • Authentication updates credential last_used_at and device last_seen_at. These are ordinary runtime writes; no authenticated calls were made during this documentation task.
  • Rotation revokes the previous active credential. Moving a device to another school revokes its existing credentials; suspension also revokes active credentials. Owner-controlled status/configuration changes may require reprovisioning.
  • No HMAC signature, mTLS, challenge/response, or device refresh-token protocol was found in the inspected ingestion implementation.

6. NFC scan endpoint

POST https://f8ad4f13-ad39-4544-9de2-99a39f6d556c-00-1pkz80o0gbypm.riker.replit.dev/api/device/attendance/events

This is the existing student NFC attendance endpoint. It accepts one event per request. There is no inspected batch upload, offline-sync route, device-readable policy-download route, or device-authenticated event-status lookup associated with this endpoint.

Separate existing employee endpoint

Teacher/staff cards use POST /devices/employee-nfc/attendance/events with the same credential header, but a different request: employeeId (positive integer), personType (TEACHER or STAFF), nfcUid (nonempty string, runtime maximum 160), eventType (SCHOOL_ENTRY or SCHOOL_EXIT), and occurredAt. It checks active employee/card binding and applicable term NFC eligibility. This is not automatic UID-based student/employee routing. A terminal intended to accept both populations needs an approved way to choose the correct existing route; do not download a school-wide roster or invent a lookup endpoint.

Employee exact-timestamp replay can return HTTP 200 with the existing event, personType, and discrepancy. Other suppressed employee scans return HTTP 409, {"error":"Duplicate employee NFC attendance event","code":"ACCESS_DENIED"}. New employee events return 201 with event fields, personType, and discrepancy. These behaviors must not be applied to the student route, which has different duplicate handling.

Use camelCase field names. The user's conceptual device_id, card_uid, and timestamp names are not this endpoint's wire format.

HTTP 201 means a new accepted student attendance event committed. HTTP 200 means a matching keyed retry returned the original persisted event; current student display information is looked up again. Neither replay creates another attendance event nor repeats security/presence/notification writes. Exact field names come from the runtime SQL projection and current-student lookup:

10. Authorization logic

  1. Read UID locally, then send an authenticated single-event request.
  2. Backend derives credential/device/school identity; checks credential validity, current school binding, active device, and configuration.
  3. Backend resolves the UID in that school through nfc_cards joined to students. Both card and student must be ACTIVE and belong to that school. An optional supplied student ID must match.
  4. Existing manual school locks, student subscription access, and identification policy are checked. NFC_AND_BIOMETRIC currently permits either NFC or fingerprint in this handler; it does not implement a paired two-factor scan.
  5. Validate event/time; classroom entry requires a current student class matching the device class.
  6. Inside a transaction, revalidate/lock the device and credential against concurrent moves/rotation and require NFC/HYBRID device type. A supplied key is checked under a transaction lock: matching existing actions receive a 200 replay after current security validation, while conflicting reuse receives 409. New actions acquire the existing per-device/person/type suppression lock and check duplicates.
  7. Insert the attendance event, resolve current student display details, reconcile attendance anomalies, and perform entry/exit NFC security integration. Security checks may reject inactive readers/locations, missing reader ENTRY/EXIT permissions, expired cards, missing current academic placement, and related identity/eligibility failures. A configured legacy reader without a security-reader mapping can remain usable with unknown security location.
  8. On rejection the attendance transaction rolls back. On success it commits and returns 201. Notifications are queued, not proof of physical delivery. Notifications failing in the best-effort communication portion need not invalidate attendance.

Authenticated NFC entry/exit 403/404 denials with usable UID/time can persist a separate rejected security tap after rollback. Audit persistence failures do not turn denial into acceptance. Device provisioning/assignment/credential changes are audited, attendance is persisted, and security events/presence are maintained. Duplicate 409 is returned directly, not handled as the same denial-audit path. Firmware has no direct audit-write requirement.

11. Device-school relationship

platform_devices.school_id is the current school. device_credentials binds issued credentials to device and school; device_school_bindings and assignment history preserve past bindings. Ingestion trusts the credential/current school relationship, not a client-selected tenant. A device move must not rewrite historical attendance. Platform Owner performs linking; the terminal cannot self-authorize a school.

12. Card-school relationship

nfc_cards stores UID, school ID, nullable student ID, status, and lifecycle/history data. An active student card must resolve to a student in the same school. Owner-controlled provisioning/activation and the existing authorized assignment workflow remain unchanged. New student assignment/activation requires an active configured NFC-capable reader linked to the school. A prepared assignment is not automatically an active/unlocked card.

School membership, active status, and assignment are backend facts. Firmware must not assume ownership from UID prefixes or an independently maintained roster. An old card must not authorize a student after school-transfer or replacement relationships invalidate it.

13. Multiple-device behavior

Yes: an active School A student card can be resolved on both active/configured NFC devices A1 and A2 with valid School A credentials. Student lookup is school-bound, not individually device-bound. Assignment rejects manually supplied device IDs; readers are inherited through the school, including subsequently linked readers.

This does not bypass classroom-reader class matching, identification policies, subscription/manual locks, reader location/permissions, or other security checks. Duplicate suppression includes device ID, so the same card/time/type submitted through two different devices is not globally deduplicated by the student route.

14. Offline behavior

A full offline synchronization protocol is not currently implemented. The online endpoint can accept individually replayed timestamped events within its 24-hour lookback; that is limited replay capability, not offline authorization, batch synchronization, cursor-based reconciliation, or a guaranteed exactly-once queue.

  • Terminal-local buffering is possible firmware work, not a backend feature verified here. If agreed separately, keep the actual UID, eventType, identificationMethod, original occurredAt, a stable idempotencyKey for that logical event, and local queue state. The key is 8–128 characters and must be reused, not regenerated, during retries. Keep credentials separately in secure storage.
  • Maximum supported/recommended queue count: not specified by the API. No numeric capacity, batch size, flush rate, or retention SLA is established. Do not claim unlimited storage or a supported queue limit.
  • While offline the backend cannot verify current device/card/student status. Keep the event pending/unverified; do not show server-confirmed success or claim permission to open a gate.
  • After restoration, submit one event per request with its original timestamp through the same endpoint. Conservative sequential replay is an integration recommendation, not a built-in protocol guarantee.
  • Authorization uses current device/card/student eligibility at replay time, not an offline snapshot. A later school move, revocation, rotation, class change, or expired card can cause rejection.
  • Events older than 24 hours are rejected. Do not rewrite old timestamps to now. Preserve them for authorized operator review; there is no device-authenticated historical import endpoint documented here.
  • A duplicate 409 must be handled separately from a confirmed new 201 receipt; see retry limitations below.

15. Retry / idempotency / timeout behavior

Student idempotency uses the existing school/dedupe unique index: a SHA-256-derived namespaced dedupe key includes authenticated school, device, and supplied idempotencyKey. Raw keys are not stored. A transaction lock serializes key lookup and insertion. Matching means the same normalized student, card, class, identification method, event type, and instant. Optional assertions or ignored fields do not change that attendance action. Credential rotation does not change the key scope; school/device changes do.

Separately, scan suppression remains a rolling ± configured seconds around occurredAt, with a default of 30 seconds and minimum of zero. The match uses school + student + device + eventType, regardless of supplied keys. No-key requests keep the original random dedupe-key behavior.

  • Retry using the same original key and timestamp/body. Changing the normalized action with the same key returns a conflict. A different key/time can create a new record only when normal suppression and authorization permit it.
  • HTTP 201 is a confirmed new accepted receipt; a matching keyed retry returns 200 with the original event ID and persisted timestamps. Without a key, a lost response followed by 409 remains ambiguous and does not return the earlier receipt.
  • Do not automatically interpret 409 as authorization to repeat physical gate actuation. A new local tap inside the suppression window can also produce 409.
  • Stop unchanged retries for 400/401/403/404. Separate expired/revoked credentials from transient network problems and involve the authorized operator.
  • For transport/5xx failure, bounded retry with backoff and jitter is firmware guidance, not an API-specified retry schedule. Preserve key/time; keep uncertain events pending until a receipt. Current credential, card, student, policy, subscription, security, and timestamp checks still apply. Do not retry after the timestamp window expires.
  • No endpoint-specific timeout, terminal response deadline, latency SLA, or retry-after contract is configured in the inspected attendance handler/server entrypoint. Agree the device timeout before deployment; no particular timeout is guaranteed here.
  • Attendance event_date is derived from the UTC ISO date slice. Other school-window/security logic can use Africa/Lagos. Preserve an explicit timezone and test around local midnight; do not assume every report uses the same date boundary.

16. NFC UID requirements

  • Send nfcUid as a JSON string, never a decimal integer, byte-array JSON, or raw binary body. Preserve leading zero bytes.
  • The database stores UID as text. No universal hexadecimal-only format, separator convention, byte order, or MIFARE/ISO14443-A/RC522 model certification is declared in the inspected integration. There is no card-memory read or MIFARE-sector authentication protocol in the HTTP API.
  • Student ingestion applies String(value).trim(), then compares nc.uid = suppliedUid exactly. It does not uppercase, lowercase, remove colons/spaces within the UID, reverse bytes, or decode hex.
  • Card provisioning/assignment detects existing UIDs case-insensitively but does not establish universal uppercase storage. Employee ingestion uses a case-insensitive UID lookup. Do not assume the employee behavior applies to students.
  • OpenAPI/shared input declares min 4, max 128 characters. Student scan runtime does not enforce a UID-specific min/max; text storage has no declared UID column length. Rejected-security-tap auditing accepts only nonempty UIDs up to 160 characters. Use the documented 4–128 envelope for new integrations, without claiming it is runtime enforcement or changing existing records.
  • For an RC522, firmware must serialize the UID bytes into the exact representation used when that physical test card was provisioned. If provisioning confirms a zero-padded uppercase hex string in reader byte order, bytes 04 A1 B2 C3 D4 E5 F6 become "04A1B2C3D4E5F6". That is conditional guidance, not a universal backend conversion rule.
  • Confirm one real Development test-card read against its stored UID before broader firmware work. Do not guess byte reversal, padding, separators, or casing. A mismatch must be resolved by authorized provisioning/firmware configuration, not an invented backend normalization change.

18. Security requirements

Provide only a dedicated Development device credential for the authorized test device. Store it securely, never display it, and keep it out of serial-console logs, analytics, repository files, HTTP URLs, shared screenshots, and support attachments. Use verified HTTPS; do not disable certificate validation. UID-only cards can be copied and are not cryptographic proof of a person's identity.

Never provide or store on the terminal: Production database credentials; DATABASE_URL; Clerk secret keys; Replit account credentials; Platform Owner credentials; School Admin credentials; parent/student passwords; payment provider secrets; or Production API secrets. Human provisioning stays with the authorized operator. No real secret appears in this guide.

Use synthetic/minimal Development test data. Successful receipts include student names and class/session information; minimize local retention and erase them when no longer needed. An offline queue contains personal-access information and must be protected. Do not expose full rosters or extra internal administration APIs merely to support firmware convenience.

20. Known limitations — Integration Gaps — Requires Separate Development Work

  • No literal ALLOW/DENY decision contract, physical gate-control command, pickup authorization, or actuator integration. Existing attendance/security identity validation is not a complete physical-security terminal protocol.
  • No full offline synchronization, batch API, queue-size contract, device-side authorization cache, or historical device import beyond the timestamp window.
  • No separate device-authenticated event-reconciliation lookup was found. Keyed replay returns the existing event only after current authorization/time checks. Cross-device suppression is intentionally not global.
  • No universal UID encoding/normalization or hardware-family compatibility promise. Student and employee UID matching behavior differs.
  • No unified student/teacher/staff UID-only dispatch endpoint; employee scans require employee ID/person type.
  • Remaining OpenAPI/runtime mismatches: UID requirement/length enforcement, default NFC method, runtime schoolClassId vs documented classId, and incomplete error-status documentation. Generated shared types are not proof of handler validation.
  • No configured terminal latency/timeout SLA or retry schedule. No physical hardware or authenticated scan acceptance was verified in this task.

These remaining gaps are reported only. Idempotency was implemented in the existing Development endpoint using the existing database structure; no migration, permission/payment change, Production change, or parallel NFC architecture was introduced.
